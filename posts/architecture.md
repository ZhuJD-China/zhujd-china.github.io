# 纯静态博客的架构哲学

本站的技术选型只有一个原则：**部件越少，系统越稳**。

## 整体架构

```
┌─────────────┐     GitHub API      ┌──────────────┐
│  posts/*.md │ ──────────────────▶ │  文章自动发现  │
└─────────────┘                     └──────┬───────┘
                                           │ fetch
                                           ▼
┌─────────────┐     marked.js       ┌──────────────┐
│   浏览器     │ ◀───────────────── │  Markdown渲染 │
└─────────────┘                     └──────────────┘
```

## 三个关键设计

### 1. 零配置的内容发现

博客不维护任何文章清单。首页加载时通过 GitHub Contents API 读取 `posts/` 目录：

- 新增 `.md` 文件 → 自动出现在首页
- 删除文件 → 自动消失
- 无需注册、无需配置文件

### 2. 前后端"分离"的假象

所有"动态"行为都发生在浏览器端：

- 文章列表由 API 动态生成
- Markdown 在客户端实时渲染
- 阅读进度、搜索、标签过滤均为本地计算

于是 **GitHub Pages 只需要做一件事：正确返回静态文件**。这正是它最擅长的事。

### 3. 优雅降级

- API 限流时 → 使用本地缓存（10 分钟 TTL）
- 无网络本地预览 → 兜底清单 `posts/index.json`
- CDN 加载失败 → 纯文本降级显示

## 为什么不用 Hugo / Hexo / Jekyll？

它们都是好工具，但对我而言：

| 方案 | 需要 |
| --- | --- |
| 静态站生成器 | 本地环境 + 构建流程 + 主题学习成本 |
| 本站方案 | 一个浏览器 + 一个 `.md` 文件 |

写作的最大敌人是**流程摩擦**。当发布一篇文章只需要"保存文件 + 推送"时，写作的心流才不会被工具打断。

> 最好的架构，是让你忘记架构的存在。
