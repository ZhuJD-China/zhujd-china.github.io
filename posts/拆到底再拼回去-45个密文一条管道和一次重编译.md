## 1. 开盒：`/UI/101` 与已知明文攻击

上期给 `/UI/101` 的判词是"熵 7.8、198 KB、单字节 XOR 没开门"。这期换思路：**别猜算法，猜明文**。

PE 资源里封的八成还是 PE 或托管程序集，而 PE 头的字节几乎全是已知的：`MZ` 魔数、`e_lfanew` 指向的 `PE\0\0`、可选头里 `0x20B`（PE32+）。拿这些已知字段去对拍密文，重复 XOR 的周期当场立住——**周期 32 字节，密钥就是密文自己**：

```python
# 探针思路（实际脚本多轮试错后收敛到这版）
cipher = blob[:64]
for period in range(1, 65):
    key = xor(cipher[:period], b'MZ' + ...模板字段...)   # 已知明文对拍
    plain = xor_repeat(blob, key)
    if plain[0:2] == b'MZ' and plain[0x3c:0x40] 结构自洽:
        ok(period); break        # → period = 32
```

解出来是一条完整的 .NET 程序集：`FLiNGTrainerGUI_WPF.exe`。交给 `ildasm /text /bytes /utf8`，得到 1.47 MB 的 IL 全文（`UI_101.il`），37 个类。上期"UI 是 .NET + WPF 写的"是动态侧推断，到这里是**源码级实证**。

资源树同时全枚举了一遍，顺手把"有没有第三块 PE"这个悬案结了：

```
/COVER/117/2052   73 KB，熵 7.99     封面图（对图，无结构可言）
/REMOTE/246       4 字节 ffffffff     远程开关标志位（1 个 dword）
/REMOTE/250       TrSpeedHack_x64.dll 第二块 PE（第 9 节开箱）
/UI/101           198 KB，熵 7.8      WPF 程序集（本节）
/WAVE/103,104                       按键音效
图标 ×4、VERSION、requireAdministrator 清单
```

**没有第三块 PE。** 上期"藏在资源里的第二块 PE"的说法准确无误——就两块，一个本尊一个变速 DLL。

37 个类里，`MainWindow`、`Utils`、`AppSettings`、`TrainerSettings`、`LoginResult`、`UILanguage`、`UIText` 几个核心的分工很清楚：纯 UI 加设置持久化，9 个 P/Invoke 全是 `GetAsyncKeyState`、窗口句柄这类轻量活——**托管层不碰内存也不碰进程**，重活全在原生壳那边。这个分层到第 4 节会变成理解整个架构的钥匙。

## 2. 托管层的物证：URL、登录，和两条 TLS 的归案

IL 里捞网络调用，三个关键词一抓一个准：`WebClient`、`DownloadString`、`ServicePointManager.set_SecurityProtocol`（强制 TLS 版本，老代码的经典动作）。托管层用的是 `System.Net.WebClient`——上期看到的 `winhttp/ws2_32/schannel` 四件套，就是 .NET Framework HTTP 栈在运行时拉起来的，宿主 EXE 的导入表从头到尾干干净净，两边谁也没说谎。

URL 拎出来一串，全在作者自己的地盘上：

```text
更新检查 : https://flingtrainer.com/wp-json/trainer-api/update-page?name=<修改器名>&lang=<语言>
           （配套 UI 文案 "Check for trainer update" / "New version found, update trainer"）
账号登录 : https://flingtrainer.com/cn/community/api/v2/app-login.php
           （PostRequest 提交 {用户名, saved_password}，返回 LoginResult.Deserialize）
社区链接 : flingtrainer.com/cn/community/threads/4260/、support_the_author、patreon、forums……
国内链接 : https://www.3dmgame.com/flxgq.html
           https://bbs.3dmgame.com/thread-<帖子号>-1-1.html   （原生侧运行时拼接）
```

域名有了，DNS 一锤定音：

```text
flingtrainer.com  A    : 104.26.14.72, 172.67.73.26, 104.26.15.72
              AAAA : 2606:4700:20::681a:f48,
                     2606:4700:20::ac43:491a,   ← 就是它
                     2606:4700:20::681a:e48
```

上期抓到的连接端点是 `2606:4700:20::ac43:491a`——**逐字节命中 flingtrainer.com 的 AAAA 记录**，而且上期已经注明这个 v6 地址的低 32 位对应 A 记录里的 `172.67.73.26`，v4 v6 对得上。两条 TLS 的身份不用中间人、不用内存 dump，一行 `Resolve-DnsName` 就交代了：**flingtrainer.com 的更新检查 + 账号登录通道**。

顺带两条安全观察，都在"它不咬人但你该知道"的范畴：

1. **登录凭据明文流转。** `AppSettings` 里躺着 `saved_password` 字段，配置文件名 `settings.json` 也在——密码以明文字段参与整个生命周期（是否落盘到 `settings.json` 标**推断**，没做落盘验证）。
2. **`LoginResult` 是作者自定义的登录结果类**，配合 `TrainerID`（长度不足 5 位回退 `"none"`）——这台修改器背后有账号体系，绑的是作者论坛的身份。

## 3. 管道终局：服务端在 IL 里

上期最漂亮的一条推断是"管道服务端在托管层"——证据链很紧但没实证。这期直接在 IL 里翻到了：

```il
.field private class [System.Core]System.IO.Pipes.NamedPipeServerStream m_named_pipe

.method family hidebysig instance void InitializeNamePipe(string name) cil managed
    ldarg.0
    ldarg.1                 // name
    ldc.i4.3                // PipeDirection.InOut
    ldc.i4.1                // maxNumberOfServerInstances = 1
    ldc.i4.0                // PipeTransmissionMode.Byte
    ldc.i4  0x80000000      // PipeOptions.Asynchronous
    newobj  instance void [System.Core]System.IO.Pipes.NamedPipeServerStream::.ctor(...)
    stfld   ...MainWindow::m_named_pipe
    callvirt instance void ...WaitForConnection()      // 等原生壳来连
```

构造参数和调用点全对上了：两处调用都是 `ldstr "FLiNGTrainerNamedPipe_"` + `Process.GetCurrentProcess().Id` 拼名字再喂给 `InitializeNamePipe`——**服务端在 WPF 的 `MainWindow` 里，用的是 .NET 的 BCL，不需要任何 P/Invoke**。上期全文件搜不到 `CreateNamedPipe` 的最后一块拼图，原来人家根本不走 Win32。

原生侧的客户端（上期已解剖的 `0x3DAC0`）和托管侧的服务端，是同一件事的两半：

```text
原生壳（client，句柄存 [this+8]）              WPF GUI（server，m_named_pipe）
─────────────────────────────────────────────────────────────────────
  查 GetCurrentProcessId()
  拼 \\.\pipe\FLiNGTrainerNamedPipe_<自己的 pid>
  Sleep(10)/WaitNamedPipeW 轮询，10 秒预算
  CreateFileW(GENERIC_READ|WRITE)  ──────▶  WaitForConnection() 返回
        │  [i32 len][ASCII "CHADURL"]  ──▶  ReadString() == "CHADURL"
        │  ◀──── [裸 i32 LE = 1]           WriteValue(1)
        │  [i32 len][UTF-16 URL]       ──▶  ReadUnicodeString() → UrlAdCH
```

触发时机也追到了：线程 `0x328A0` 的主干走到 `0x41920`——`找到游戏进程 → 加载辅助数据 → new 一个会话对象 → 拉起管道`。**一条会话，生命周期跟"游戏在不在"走。**

于是整机的进程内架构可以画完整了，一句话版本：**一个 EXE 里跑着两套运行时，MMF 走状态共享，命名管道走请求/应答，命令集两侧对账严丝合缝**。为什么两套？共享内存没有"应答"语义，命令要回执就得起管道——这是设计，不是冗余（"为什么不用一套"的部分属合理推断）。

## 4. 帧协议：把线节上的字节排成句子

协议不靠猜，托管侧 `MainWindow` 的读写函数在 IL 里是全裸的：

```il
ReadString():
    call   ReadInt32()                    // 先读 4 字节长度
    newarr System.Byte
    ... Stream::Read(buf, 0, len)         // 再读满载荷
    call   Encoding::get_Default()        // ANSI/GBK 解码

ReadUnicodeString(): 同上，Encoding.Unicode（UTF-16LE）

WriteValue(int32):
    call   BitConverter::GetBytes(value)
    ... Stream::Write(bytes, 0, 4)        // 裸 4 字节，没有长度头
```

所以线上的语法只有两条：**串 = `[i32 LE 长度][字节载荷]`，应答值 = 裸 `[i32 LE]`**。原生侧严丝合缝：它读应答就是 `ReadFile(h, buf, 4, ...)`，正好一个 int32。

命令全集 12 条，两侧对账（原生加密持有 / 托管明文持有）拿全的：

```text
CHADURL                   握手 + 下行 URL（存进 UrlAdCH 字段）
RESETCHADURL              复位
WMURL                     打开页面
SETTINGS / SAVE_SETTINGS  设置同步/保存
SET_GAMEPASS_EXE_PATH     下发 GamePass 启动路径
ENABLE_ANTICHEAT_BYPASS   反作弊绕过开关        ← 开关存在，运行时链路未追
TRAINER_INITIALIZE        初始化（GUI 侧置 SkipAutoActivate 标志）
CUSTOM_INIT_MESSAGE       自定义启动消息（回 UI 线程 Dispatcher.Invoke）
CHECK_UPDATE              更新检查（下读 UTF-16 版本号 + ANSI 更新 URL）
{CMD}_SetLanguage         语言切换（{CMD}_ 模板族）
{CMD}_InstallAnticheatBypass
```

分发器 `TrainerCall_CustomCommand` 的语义也齐：逐个 `String::op_Equality` 比对，命中回 `WriteValue(1)` 再干活，**没命中回 `WriteValue(0)` 当 NACK**——协议连错误路径都是全的。

这一节最想讲的是它和上期的关系：**上期在原生侧看到一坨天书密文，这期在托管侧看到同一批明文——两边互为字典**。原生的加密串给托管的明文做完整性验证，托管的明文给原生的密文做内容注解，双端对账是这期最顺手的一件武器，后面第 6 节破字符串保护时还会再用一次。

## 5. 彩蛋：`CHADURL` 是明文躺那儿的

破加密之前先讲个笑话，出自 `0x40f40`（原生侧的握手函数）：

```asm
mov   dword ptr [rbp - 0x39], 0xd6e42661   ; 密钥老老实实存了
mov   dword ptr [rbp - 0x35], 0x44414843   ; 'C' 'H' 'A' 'D'
mov   dword ptr [rbp - 0x31], 0x4c5255     ; 'U' 'R' 'L' 00
xorps xmm0, xmm0
movups xmmword ptr [rbp - 0x29], xmm0      ; 尾部清零
lea   rcx, [rbp - 0x35]
call  strlen                               ; 直接当明文用！
```

**密钥存了，解码器没调。** `"CHADURL"` 两个 dword 裸放，`strlen` 一量就走。全文件 45 个加密位点里，就这一处是明文——是疏忽还是刻意的反"自动化解密"诱饵，无从考证。它好玩的地方在于：我最开始按位点规律解它，得到一串乱码，差点当成算法 bug 追——**规律的例外本身就是信息**。

## 6. 破字符串保护：从三条指令到一条 LCG

上期为什么全文件字符串扫描扑空？`OpenProcess`、`WriteProcessMemory` 这些名字**从来就没以明文形式存在过**——它们以密文形态躺在 `.text` 的指令立即数里，运行时现解现用，解码函数二十多个同族变体（`0x33d20`、`0x338b0`、`0x39d70`……同一算法按输出类型/长度模板实例化）。

突破口是解码器本体的约减例程。反汇编出来就是三条乘移的影子：

```asm
; 计算 a mod 0x7FFFFFFF（2^31 − 1），纯整数指令序列
mul   3 / 取商高 32 位 → edx
sub / shr 1 / add 回填
shr   30            ; 商 q
imul  0x7FFFFFFF
sub   回 a          ; 余数
```

翻译成公式：

```text
reduce(a) = a − ((a>>1 + ((3a)>>32)) >> 30) × 0x7FFFFFFF   ≡  a mod (2³¹−1)

状态机（完整的字符串保护算法）：
    state₀ = key = 0xD6E42661
    plain[i] = (stateᵢ & 0xFF) XOR cipher[i]
    stateᵢ₊₁ = (stateᵢ × 0xBC8F) mod 0x7FFFFFFF
```

先拿 10000 个随机数验证 `reduce(a) == a % 0x7FFFFFFF`，全过；再拿二进制里的真实密文对拍，全过。**这是一条 LCG（线性同余）流密码**，乘数 `0xBC8F`、模数 `2^31−1`、种子 `0xD6E42661`，三个常量把整个保护方案钉死了。

接下来是这期最重要的一个方法转变：**不再追调用点，改扫密钥**。`mov dword [栈槽], 0xd6e42661` 这个立即数在 `.text` 里出现几次，加密点就有几个——45 处，一处不漏。每个位点的形态都一样：密钥后 4 字节起是密文，密文由 `movdqa`（16 字节 rip 相对块）+ 若干 `dword`/`byte` 立即数拼装：

```asm
mov   dword ptr [rsp + 0x20], 0xd6e42661     ; 密钥
movdqa xmm0, xmmword ptr [rip + 0x9f5b9]     ; 密文 16B
movdqu xmmword ptr [rsp + 0x24], xmm0        ; 数据基址 = 密钥槽 + 4
mov   dword ptr [rsp + 0x34], 0xb2ce8f73     ; 续 4B
mov   dword ptr [rsp + 0x38], 0x36f1ea2d     ; 续 4B
mov   byte  ptr [rsp + 0x3c], 0xde           ; 尾 1B
mov   r8d, 0xd6e42661                        ; 解码器第 3 参 = 密钥
lea   rdx, [rsp + 0x24]                      ; 第 2 参 = 密文
lea   rcx, [rsp + 0x40]                      ; 第 1 参 = 出串缓冲
call  0x1400338b0                            ; 解码器变体之一
```

写个探针把 45 个位点全机器解一遍——中间踩了两个坑值得记下来：一是 rip 相对的 `movdqa` 载荷有时出现在**密钥存储之前**（向前回溯范围不够会漏前 16 字节）；二是 `xmm0/xmm1` 两段存储要**按寄存器配对**回溯，按"最近一条"配对会拿错源。修完这两个 bug，45 个位点全部落网：

- **44 处密文**解出明文（含 `CHADURL` 那处的对头——它没密文，见第 5 节）；
- 归并去重后 **39 个唯一串**（4 个 DLL 名各重复 2–4 次，都是"加载→解析"的成对代码）；
- 外加一处**分片存储**：`https://flingtrainer.com/tag/` 被拆成 16+16 两段 xmm 存，实际是一次编码 32 字节——第二片从头解是乱码，按状态续算 16 步再解就顺了，密文自己证明了自己是流密码。

## 7. 45 个位点，39 个唯一串：隐藏导入表全貌

三读这张表：

1. **提权链是教科书级的**：`OpenProcessToken → LookupPrivilegeValueW(SeDebugPrivilege) → AdjustTokenPrivileges`，先把自己升到能碰任意进程的权限，再干活。上期清单里"要求管理员清单"是第一层，这是第二层。
2. **注入能力矩阵齐全**：读/写内存、分配/查询/保护远程内存、`CreateRemoteThread`——经典注入四件套一个不缺。但注意：**表里没有 `CreateNamedPipeW`**。原生侧只有客户端资格，服务端只能在托管层——第 3 节的实证和这张表互为闭环。
3. **`CreateProcessW` + `ShellExecuteW` + `GetAsyncKeyState` 各有归属**：前者对上 `SET_GAMEPASS_EXE_PATH` 和 GUI 的启动按钮（GamePass 版游戏要拉起来），后两者一个开 URL（捐赠页/帖子链接），一个说明**原生侧自己也在扫热键**——热键不只托管层一套，双端都有，这是上期没料到的。

## 8. 23 项功能与作者，最终版

功能表在第 1 期第 10 节已经立全（13 条数字键 + 10 条 Ctrl 组，四路证据对账），这期补三个收口结论：

- **`gamespeed_f` 有了硬件对应物**——资源里的 `TrSpeedHack_x64.dll`（第 9 节），变速功能不是 CE 脚本钩出来的，是单独一个 DLL 进游戏里干的（两者的分工细节标推断）。
- **热键双端实现**：托管层 9 个 P/Invoke 里的 `GetAsyncKeyState` 管 UI 开关，原生隐藏表里的 `GetAsyncKeyState` 管原生逻辑——同一套按键，两套监听。
- **作者归属维持第 1 期的五路结论**：原作者 = 风灵月影（FLiNG）；23 条 CE 脚本 = 同一人同源、无第三方署名；联网后台 = `flingtrainer.com` 自有域名；国内渠道 = 3DMGAME；"谁重编译了谁" = 推断级未定案。这期新增的 URL 证据（更新/登录/捐赠全在 flingtrainer.com）只会让第一格更硬。

## 9. TrSpeedHack 开箱：一个变速 DLL 的底细

`/REMOTE/250` 拆开看（结论先行：**纯游戏内变速组件，无管道、无网络、无注入能力**）：

```text
文件      : TrSpeedHack_x64.dll，x64，ImageBase 0x180000000
时间戳    : 2024-03-31 06:09:52 UTC
结构      : .text/.rdata/.data/.pdata/_RDATA/.rsrc/.reloc，常规 MSVC 形状
导入      : KERNEL32（大堆 UCRT 启动件）
           + VirtualAlloc/VirtualFree/VirtualProtect/VirtualQuery/GetSystemInfo
           + CreateToolhelp32Snapshot/Thread32First/Thread32Next
           + SuspendThread/ResumeThread/OpenThread
           + GetThreadContext/SetThreadContext/RtlCaptureContext/RtlVirtualUnwind
           + GetProcAddress/GetModuleHandleW/FlushInstructionCache
           + QueryPerformanceCounter
           + WINMM.dll: timeGetTime        ← 钩子目标，直连导入
导出      : 5 个，全部只有序号没有名字（ordinal-only）
```

读法三行：

1. **`timeGetTime` + `QueryPerformanceCounter` 直连导入**——游戏计时就这两个源头，钩子要改谁一目了然。改这两个，整个游戏的世界速度就跟着变，`gamespeed_f` 的物理实现就是它。
2. **`Thread32 枚举 + Suspend/Resume + Get/SetThreadContext + VirtualProtect + FlushInstructionCache`**——标准的"挂起全部线程 → 改码 → 恢复"内联钩子施工法：先让进程停下来，改字节才没有竞态。
3. **5 个匿名导出**是给宿主（修改器本尊）留的调速接口。宿主怎么把 DLL 弄进游戏（`REMOTE/246` 那个 `ffffffff` 标志位干什么用、走 `CreateRemoteThread` 还是别的），**没有追，进新留白**。

## 10. 重建：对照表、修改点与优化点

到这儿"看懂了"。接下来是这期的正题：**把看懂的东西写回源码**。工程落在 `fling_trainer_rebuild/`，先给对照表——每一行都是"原样本怎么做 / 我重写成什么样"：

| 层 | 原样本 | 重建源码 | 关系 |
| --- | --- | --- | --- |
| 字符串保护 | LCG 流密码，key `0xD6E42661`，20+ 个解码器模板变体，45 位点 | `lcg_codec.h` 单一实现 + **补写的 `encode()`** | 算法 1:1（37 条向量验证），接口现代化 |
| 导入表 | 39 个 API/串名加密藏 `.text`，动态解析 | `attach.h` 明文调用等价 API | 能力等价，去混淆 |
| 管道客户端 | `0x3DAC0`：Sleep(10) 轮询，10 秒预算 | `pipe_client.h` 忠实版 + 优化版（编译开关切换） | 指令级复刻 + 可优化 |
| 管道服务端 | WPF `m_named_pipe`（明文 IL） | `pipe_server.cs` 同名同参复刻 | 方法级复刻，`csc` 可编译 |
| 协议帧 | `[len][payload]` + 裸 i32 ack | `pipe_proto.h` | 帧格式 1:1，命令全集 12 条 |
| AOB 定位 | CE 脚本 `aobscanmodule` 内联 | `aob_scan.h` 通配扫描 + 1MB 分块 RPM | 能力等价 + 分块优化 |
| 功能开关 | 23 条脚本 + GUI 事件散落 | `features.h` 单一数据表 23 行 | 结构性修改 |
| 热键 | `GetAsyncKeyState` 电平轮询 | `hotkey.h` 上升沿触发 | 语义不变，防按住连发 |

**可修改**：功能表一行一项（ID/热键/中文名/脚本引用），加功能 = 加一行数据，引擎不动；解码器带 `encode()`——原实现只有解码，密文是编译期外部工具压的，现在改密钥、加新串都在源码层完成。

**可优化**，六条，每条都落了代码：

1. **管道连接**：原版 10ms 粒度轮询（10 秒预算 = 最多 1000 次 `Sleep`+`WaitNamedPipeW` 往返）；优化版 250ms 切片，往返 ≤40 次，连接语义不变。
2. **AOB 扫描**：1MB 分块读 + `(patlen−1)` 重叠窗口 + 首字节预筛 + `VirtualQuery` 跳过 GUARD/NOACCESS 页——块间不漏报，系统调用次数降一个量级。
3. **写路径带回滚**：`VirtualProtectEx` 改属性 → 写 → **恢复原属性** → `FlushInstructionCache`。原样本的写路径不带这层（逆向时看到的裸写）。
4. **功能表数据化**（见上）。
5. **热键上升沿**（见上）。
6. **明文 + 可选加密展示**：日常开发用明文，要验证加密链时把向量表喂回 `decode()`。

**不能验证的，也写清楚**：23 条补丁的实机匹配需要游戏本体，本次没做；管道自测是本进程环回，不碰原样本进程；`SeDebugPrivilege` 在非管理员会话里拿不到（自测里如实标 skip 而不是假绿灯）。

## 11. 编译与自测：18 盏绿灯

构建工具是本机现成的：VS2017（MSVC 14.16.27023，WinSDK 10.0.17763.0）+ .NET Framework 4.x 的 `csc.exe`（v4.0.30319）。一条 `build.bat` 串起来：`vcvars64.bat` → `cl /std:c++14 /utf-8 /O2` 编原生侧 → `csc /target:library` 编托管侧 → 自动跑自测。

过程不是一次过的，三次翻车都是好素材：

1. **GBK 控制台把 build.bat 自己咬了**：bat 里写了中文注释，cmd 按 GBK 解析 UTF-8 字节，注释行被当命令执行，`'Community' 不是内部或外部命令` 满屏飞。结论：**批处理文件纯 ASCII + 强制 CRLF**，中文注释只进 README。
2. **三个编译错各值一回**：命名空间 `inline` 变量要 `/std:c++17`（改 `static`）；`SE_DEBUG_NAME` 在非 UNICODE 下是窄串（`LookupPrivilegeValueW` 换 `…A`）；`OpenProcessToken` 一族在 `advapi32.lib`（默认不链，补 `/link … advapi32.lib`）。
3. **自测断言过严**：密文尾部有 16/24 字节对齐残渣，原实现语义只保证到 NUL——断言改成"前缀到 NUL"才反映真实契约。**测试写得比实现还苛刻，也是一种 bug。**

最终自测输出，原文贴上来（不筛、不美化）：

```text
== fling_trainer_rebuild selftest ==
[PASS] codec: embedded vectors decode to plaintext
[PASS] codec: encode() round-trips to binary ciphertext
[PASS] split-url: 16+16 xmm chunks reassemble
[PASS] aob: wildcard pattern hits planted offset
[PASS] aob: exact pattern hits planted offset

[PASS] aob-remote: RPM chunked scan finds marker in own image
```

几个绿灯的含金量说明：`codec` 两行 = 37 条密文向量逐条对拍二进制原文；`split-url` = 分片续算状态的独立验证；`pipe` 五行 = **新建管道服务端线程 → 原生客户端按 `FLiNGTrainerNamedPipe_<pid>` 连上 → 发 `CHADURL` 帧 → 收裸 4 字节 ack=1 → 回 UTF-16 载荷**，整条协议环回实测；`aob-remote` = 用 `ReadProcessMemory` 在自己镜像里扫出埋好的标记，远程路径真跑；`privilege` 那行是**如实的黄灯**——当前会话非管理员，提权路径本就没条件验证，不伪造成功。

## 13. 边界、风险与方法论

先划边界。重建工程是**逆向结论的可执行验证**，不是复刻品：不含反作弊绕过实现，不带游戏侧补丁数据，`--attach` 默认只读，写路径只在演示模式对自己的缓冲区动刀。它验证的是"我理解对了"——算法、协议、结构能被独立重写并测绿，比任何文字描述都硬。

风险提示沿用上期并加两条：样本未签名、信任面大，这没变；新增——**这台修改器会收集账号凭据**（第 2 节），以及变速/内存修改在多人场景的账号风险不因为"单机游戏"就自动豁免。用之前想清楚这两条。

方法论这期沉淀四条，比上期多了两条实战的：

1. **已知明文攻击先行。** 别一上来猜算法，PE/PE 程序集的头部字段几乎是白送的明文，`/UI/101` 十分钟就该开门。
2. **拿常量当抓手，别追调用点。** 45 个 `0xd6e42661` 立即数比 45 个调用点好找得多——**加密的密钥本身是解密者的路标**。
3. **双端对账。** 原生侧密文和托管侧明文互为字典，一条链的输出是另一条链的输入，对不上的地方就是没解完的地方。
4. **重建即验证。** 把算法重写成能编译、能跑、能测的代码，全绿的那一刻，"推断"才升级成"结论"。

工具命令照例收尾：`py -m pip install pefile capstone`、`ildasm /text /bytes /utf8 /nobar`、`vcvars64.bat` 一条线。没有 Ghidra，1.6 MB 拆到了协议字节级；没有游戏，重建工程自测 18 盏全绿。下一期想碰的靶子已经有了——新留白里那条"反作弊绕过的运行时链路"，是整份样本里最后一块没翻开的石头。
