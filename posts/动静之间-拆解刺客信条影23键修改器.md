这期的解剖对象躺在下载目录里挺久了：`Assassins Creed Shadows v1.0-v1.1.8 Plus 23 Trainer.exe`，FLiNG 出品的《刺客信条：影》修改器，23 个热键。来路是盗版站，下载页自己都写着"360 会报毒，请添加信任"。这种东西的正确处理方式不是双击，是把它摊平在手术台上，让静态和动态两套证据互相质证——这就是我一直想做一期的"动静结合"。

静态分析负责画骨架：入口在哪、导了哪些 API、字符串里藏了什么、代码是怎么组织的。动态分析负责验行为：真跑起来它开了几个线程、建了什么管道、往哪儿发了连接。单看任何一边都会被骗——这台机器就是最好的例子：静态看它是个"零联网"的乖程序，动态跑 12 秒，两条到 Cloudflare 的 TLS 长连接挂在那儿。到底谁在说谎，最后一节当面对质。

先说清楚：全程没碰用户的任何游戏进程，样本也没裸跑——第一次尝试被 UAC 拦下来（`WinError 740`，清单要求管理员），改成受控提权运行、逐秒采样、用完即杀。分析工具是 `pefile` + `capstone`，机器上没有 Ghidra、没有 radare2、连 Java 都没有，所以"反编译"这期全靠反汇编加人工还原伪 C——反而逼我把每段代码都读透了。

## 2. 入口链：从 0x9F4E0 一路走到 main

64 位 PE 的入口通常不是业务代码，是 CRT 的启动蹦床。反汇编出来确实是这个形状：

```asm
; ---- AddressOfEntryPoint = 0x9F4E0 ----
0x14009F4E0:  sub   rsp, 0x28          ; Windows x64 调用规约的影子空间
0x14009F4E4:  call  0x14009f94c        ; CRT 一次性初始化（security cookie 等）
0x14009F4E9:  add   rsp, 0x28
0x14009F4ED:  jmp   0x14009f36c        ; 尾跳到 CRT 续接函数，不占栈
```

CRT 续接函数干完自己的杂活之后，把控制权交给真正的 main。调用点长这样：

```asm
0x14009F451:  call  0x14009f848        ; 某初始化，返回值截进 ebx
0x14009F456:  movzx ebx, ax
0x14009F459:  call  0x1400b5cc4        ; 返回值当第 3 参（看形态像命令行串）
0x14009F45E:  mov   r9d, ebx           ; 第 4 参
0x14009F461:  mov   r8,  rax           ; 第 3 参
0x14009F464:  xor   edx, edx           ; 第 2 参 = 0
0x14009F466:  lea   rcx, [rip - 0x9f46d]  ; = 0x140000000，即 &__ImageBase
0x14009F46D:  call  0x140036f70        ; 这就是 main
0x14009F472:  mov   ebx, eax           ; 保存退出码
```

注意那行 `lea rcx, [rip - 0x9f46d]`：算出来的地址正好是 ImageBase 本身。main 的第一个参数是自己的映像基址——这个签名不是标准 `main(argc, argv)`，是这套框架自定义的。拿到这个细节花了我三轮，中间还犯过一个低级错误：查 IAT 槽位时忘了加 ImageBase，11 个地址全部 `NOT FOUND`，白跑一趟。加上基址重查，才把每个 `call [rip + …]` 钉到具体 API 上——这个失误本身就值得写进文章，后面引用 IAT 解析结果的每一处，都是修正后重跑的。

## 3. main 的开场白：DPI、COM、一根线程

main 的函数体开局就是 0x1160 字节的大栈帧，配 security cookie：

```asm
0x140036F70:  mov   qword ptr [rsp + 0x10], rbx
0x140036F75:  push  rbp
0x140036F76:  push  rsi
0x140036F77:  push  r14
0x140036F79:  lea   rbp, [rsp - 0x1060]
0x140036F81:  mov   eax, 0x1160
0x140036F86:  call  0x14009f230        ; __chkstk：0x1160 > 页大小，要探页
0x140036F8B:  sub   rsp, rax
0x140036F8E:  mov   rax, qword ptr [rip + 0xd88eb]   ; security cookie
0x140036F95:  xor   rax, rsp
0x140036F98:  mov   qword ptr [rbp + 0x1050], rax
0x140036F9F:  xor   r14d, r14d
0x140036FA2:  mov   rbx, r8             ; 第 3 参（命令行串）存进 rbx
0x140036FA5:  mov   esi, r14d           ; esi = 0，后面管道循环的计时预算
0x140036FA8:  mov   dword ptr [rsp + 0x60], r14d
0x140036FAD:  call  qword ptr [rip + 0x9849d]   ; → 0x1400CF450 = SetProcessDPIAware
0x140036FB3:  mov   edx, 2
0x140036FB8:  xor   ecx, ecx
0x140036FBA:  call  qword ptr [rip + 0x984f0]   ; → 0x1400CF4B0 = ole32!CoInitializeEx
0x140036FC0:  mov   ecx, 1
0x140036FC5:  call  0x14009ed30        ; 建上下文对象，返回值做线程参数
0x140036FCA:  lea   rcx, [rsp + 0x58]  ; 接收线程 ID 的槽位
0x140036FCF:  mov   r9,  rax            ; 线程参数
0x140036FD2:  mov   qword ptr [rsp + 0x28], rcx
0x140036FD7:  lea   r8, [rip - 0x473e]  ; = 0x1400328A0，线程入口
0x140036FDE:  xor   ecx, ecx            ; lpSecurityAttributes = NULL
0x140036FE0:  mov   dword ptr [rsp + 0x20], r14d  ; dwCreationFlags = 0
0x140036FE5:  xor   edx, edx            ; dwStackSize = 0
0x140036FE7:  call  0x1400b1b54        ; 薄封装，内部 0xB1BC4 调 CreateThread
0x140036FEC:  mov   qword ptr [rsp + 0x50], rax  ; 保存线程句柄
0x140036FF1:  test  rax, rax
0x140036FF4:  je    0x1400373c4         ; 建线程失败 → 错误路径
```

翻成人话：`SetProcessDPIAware()` 撑起高 DPI 显示，`CoInitializeEx(NULL, COINIT_APARTMENTTHREADED)` 把 COM 拉成单线程单元——这两件事加上后面满屏的 .NET 栈，基本宣告了 UI 是 WPF 写的。然后建一根线程，参数 `(NULL, 0, 0x328A0, ctx, 0, &tid)` 与 CreateThread 六参严丝合缝。

线程入口 0x328A0 我只追了开头，能确认的形状是：

```asm
0x1400328A0:  push  rbx
0x1400328A4:  sub   rsp, 0x20
0x1400328A8:  mov   rbx, rcx            ; 保存线程参数
0x1400328AB:  call  0x140041920
0x1400328B0:  call  0x14009e124
0x1400328B5:  test  rbx, rbx
0x1400328B8:  je    …                   ; 空参数则跳过后续
0x1400328BA:  mov   edx, 1
  …
```

线程肚子里是什么，留给作业了——不是回避，是这期的重点在动静对质上，线程内部的深挖值得单独一期。

## 4. 两处私货：Wine 探测与 retry-non-windows

main 往下走十几条指令，撞见第一段真正有叙事价值的代码——环境探测：

```asm
0x140036FFA:  lea   rcx, [rip + 0x9d647]      ; 0x1400D4648 = L"ntdll.dll"
0x140037001:  mov   qword ptr [rsp + 0x1180], rdi
0x140037009:  call  qword ptr [rip + 0x980b9] ; → 0x1400CF0C8 = GetModuleHandleW
0x14003700F:  mov   rcx, rax                  ; 模块句柄做下一参
0x140037012:  lea   rdx, [rip + 0x9d617]      ; 0x1400D4630 = "wine_get_version"
0x140037019:  call  qword ptr [rip + 0x98041] ; → 0x1400CF060 = GetProcAddress
0x14003701F:  test  rax, rax
0x140037022:  jne   0x14003709a               ; 查到了 → Wine 路径
0x140037024:  xorps xmm0, xmm0                ; 没查到 → 原生 Windows 路径
```

`wine_get_version` 是 Wine 的 ntdll 私有导出，原生 Windows 上必然查不到。四条指令写完了一个经典的"你在不在 Wine 里"探针。更有味道的是它的邻居：这段字符串在 .rdata 里紧挨着 `Failed to initialize trainer.`（UTF-16）和 `ntdll.dll`——失败文案和探测代码的字符串住在同一片街区，编译器按引用顺序排的，这属于静态分析白送的上下文。

原生路径这边还要做第二道探测。`0x140037024` 之后，esi 被置 1，调 `0x1400af420` 把第 3 参（rbx 里存的那条命令行串）转成宽字符 wstring，然后拿 `0x14009c3c0` 对它做子串搜索：

```asm
; needle = 0x1400D4660 = L"retry-non-windows"（17 字符 = 0x11）
; r9d = 0x11，与字符串长度逐位吻合
; 命中与否汇进 bl 这一个标志位
```

随后 `bl` 决定走哪条初始化路：

```asm
  lea   rdx, [rip + 0x9d599]   ; 0x1400D4684 = L"UI"
  mov   ecx, 0x65              ; 101，疑似 ID/错误码，语义未确证
  test  bl, bl
  call  0x140034720            ; bl = 1（原生 Windows、命令行无标记）
  call  0x140034a50            ; bl = 0（Wine 环境，或命令行带 retry-non-windows）
  test  al, al
  jne   0x14003737c            ; 返回假 → 失败路径（"Failed to initialize trainer." 的归宿）
  cmp   qword ptr [rip + 0xd8425], 0x1388   ; 全局变量 vs 5000
  jge   0x14003730f
```

拼起来的语义我只能给到推断级别：**Wine 环境与命令行里带 `retry-non-windows` 标记的进程，走同一条（0x140034a50）初始化路径；另一条路（0x140034720）头上顶着一个 5000 的阈值检查，像是重试次数上限**。0x1388 = 5000 这个数和 `retry` 这个词摆在一起，让"重试上限"的猜测挺自然，但 0x140034720 和 0x140034a50 两个函数的函数体我没有逐行展开，`ecx = 0x65` 到底是错误码还是资源 ID 也没钉死——这块标推断，不装确证。

顺带一个观察：修改器专门探测 Wine，说明它的目标用户里真有在 Proton/Wine 下玩单机的人。兼容性代码写到这个份上，算是职业素养。

## 5. 26 处 GetProcAddress：宏展开出来的解析簇

全文件 FF15 间接调用扫一遍，`GetProcAddress` 被引用 **26 次**。它们不是散落的，是排成方阵的：

```
第一簇（12 处）: 0x356e5 0x358ab 0x35a4f 0x35bf3 0x35d97 0x35f3b
                 0x360f1 0x36295 0x36450 0x3680d 0x369c6 0x36b7f
第二簇（10 处）: 0x4341f 0x435cf 0x4377f 0x43923 0x43ac7
                 0x43c6b 0x43e23 0x441d2 0x4438d 0x4513a
零散（ 3 处）  : 0x630d7 0xb502f 0xb8eee
外加 main 里   : 0x37019（上一节的 Wine 探针）
```

两簇的调用点大多间隔 0x1A4～0x1C6 字节——同一个函数体被宏或模板复制出来的痕迹，五胞胎、六胞胎排排站。单看一处：

```asm
0x1400356E2:  mov   rcx, rdi                       ; HMODULE
0x1400356E5:  call  qword ptr [rip + 0x99975]      ; → 0x1400CF060 = GetProcAddress
0x1400356EB:  mov   rbx, rax
0x1400356EE:  mov   qword ptr [rsi + 8], rax       ; 函数指针存进结构体 +8 槽位
```

解析出来的指针往 `[rsi+8]` 里塞——这是一个运行时才搭起来的函数指针表。配套的 `LoadLibraryA` 有 5 个调用点（0x3558d、0x366a4、0x432be、0x4407a、0x45039），`LoadLibraryW` 1 处、`LoadLibraryExW` 2 处。也就是说，这个程序有一张**静态导入表之外的第二套 API 表**，名字在运行时逐个换指针。

这里必须交代一次扑空，它比成功更值钱。我在 .rdata 里搜 `NamedPipe`，ASCII 命中一处，文件偏移 1101572，当时心跳都漏了一拍——管道名不是找到了吗？把上下文抠出来一看：

```
… GetModuleHandleW\0\0 \xf4\x03 LoadLibraryA\0\0 \xa9\x04 ReadFile\0\0
   ,\x06 WaitNamedPipeW\0\0 A\x02 GetCurrentProcess\0 \xda\x02 GetPrivateProfileStringW …
```

`NamedPipe` 三个词是从 `WaitNamedPipeW` 中间断出来的。这整片是标准的 PE 导入名表：每条 `[Hint: u16][名字\0]`，偶数对齐补齐——`\xf4\x03` 是 LoadLibraryA 的 hint 0x03F4，`\xa9\x04` 是 ReadFile 的 hint……全是我熟悉的加载器格式，只是夜路走多了看谁都像管道名。同理，`FLiNGTrainerTemp`（UTF-16，偏移 853312）也不是管道名，是个临时命名串。真正 的 `FLiNGTrainerNamedPipe_` 全文，ASCII 和 UTF-16 双编码搜遍全文件：**零命中**。这直接把叙事推进到下一节：这个名字是运行时拼出来的。

## 6. 导入表里没有的东西：能力藏在哪一层

把"敏感 API"清单拿去静态表里点名，结果是这样的：

```
OpenProcess        ASCII -1  UTF-16 -1
ReadProcessMemory  ASCII -1  UTF-16 -1
WriteProcessMemory ASCII -1  UTF-16 -1
CreateRemoteThread ASCII -1  UTF-16 -1
GetAsyncKeyState   ASCII -1  UTF-16 -1
SetWindowsHookEx   ASCII -1  UTF-16 -1
http://  https://  winhttp  ws2_32   全部 -1
导入表里唯一沾边的 : VirtualProtect（3 处调用）
```

一个 23 键的修改器，导入表里没有进程读写、没有键盘钩子、没有任何网络字符串。三项"外挂标配"集体缺席，可 23 条要改游戏内存的脚本明明白白躺在文件里。矛盾吗？不矛盾，这恰恰是 Windows 平台上"导入表 ≠ 能力清单"的教科书案例，能力有三条暗道可走：

其一，`GetProcAddress` 运行时解析——上一节那 26 处就是为此准备的，但有意思的是连 API 名字本身都不在文件里（双编码 -1），说明名字要么拼接构造，要么根本在托管层；其二，mscoree.dll 只导入了一个函数 `CLRCreateInstance`——这是托管宿主的入场券，UI 由 .NET 承包之后，.NET 自己的 P/Invoke 走 CLR 内部解析，宿主 EXE 的导入表根本看不见（第 10 节动态看到的 WPF 栈就是铁证）；其三，字节码层面——熵 7.8 的加密资源还躺在第 8 节没开箱。

至于热键，`GetAsyncKeyState` 和 `SetWindowsHookEx` 都不在，加上 `CoInitializeEx(APARTMENTTHREADED)`，热键大概率由 WPF 的输入系统在托管层接走，而不是原生层轮询。这是推断，但动静两侧的证据都往这个方向指。

## 7. 命名管道：0x3DC40 处的连接循环

静态搜不到名字，不代表搜不到"找名字的代码"。0x3DC40 这段是完整的管道客户端——前半截是 std::string 释放和 cookie 校验的杂活（`cmp rdx, 0x1000` 那套大块内存头回溯，尾部还挂着 `int 0x29` fastfail），真正的戏从 Sleep 开始：

```asm
0x14003DC75:  mov   ecx, 0xa
0x14003DC7A:  call  qword ptr [rip + 0x913b8]      ; → 0x1400CF038 = Sleep(10)
0x14003DC80:  lea   rcx, [rsp + 0x48]
0x14003DC85:  cmp   qword ptr [rsp + 0x60], 7       ; wstring 短字符串优化
0x14003DC8B:  cmova rcx, qword ptr [rsp + 0x48]     ; 长度>7 用堆指针，否则内联缓冲
0x14003DC91:  mov   edx, 0xa
0x14003DC96:  call  qword ptr [rip + 0x91444]      ; → 0x1400CF0E0 = WaitNamedPipeW(名, 10ms)
0x14003DC9C:  test  eax, eax
0x14003DC9E:  jne   0x14003dcb2                     ; 等到了 → 退出等待
0x14003DCA0:  call  qword ptr [rip + 0x9150a]      ; → 0x1400CF1B0 = GetLastError
0x14003DCA6:  cmp   eax, 2                          ; ERROR_FILE_NOT_FOUND
0x14003DCA9:  jne   0x14003dcb2                     ; 其它错误也退，不恋战
0x14003DCAB:  sub   esi, 0xa                        ; 预算 -= 10ms
0x14003DCAE:  test  esi, esi
0x14003DCB0:  jg    0x14003dc75                     ; 还有预算 → 回到 Sleep 继续
0x14003DCB2:  lea   rcx, [rsp + 0x48]
0x14003DCB7:  cmp   qword ptr [rsp + 0x60], 7
0x14003DCBD:  cmova rcx, qword ptr [rsp + 0x48]     ; 再取一次 c_str()
0x14003DCC3:  mov   qword ptr [rsp + 0x30], r15     ; hTemplateFile（第 7 参）
0x14003DCC8:  mov   dword ptr [rsp + 0x28], 0x80    ; FILE_ATTRIBUTE_NORMAL
0x14003DCD0:  mov   dword ptr [rsp + 0x20], 3       ; OPEN_EXISTING
0x14003DCD8:  xor   r9d, r9d                        ; lpSecurityAttributes = NULL
0x14003DCDB:  xor   r8d, r8d                        ; dwShareMode = 0
0x14003DCDE:  mov   edx, 0xc0000000                 ; GENERIC_READ | GENERIC_WRITE
0x14003DCE3:  call  qword ptr [rip + 0x914e7]      ; → 0x1400CF1D0 = CreateFileW
0x14003DCE9:  mov   qword ptr [r14 + 8], rax        ; 句柄存进对象 +8
0x14003DCED:  cmp   rax, -1                         ; INVALID_HANDLE_VALUE
0x14003DCF1:  setne bl                              ; 返回 bool：连上没有
```

还原成 C 大概是：

```c
// esi = 总预算（毫秒），函数序言从外部带进来
bool pipe_connect(ctx* self, const wchar_t* name, int budget_ms) {
    do {
        Sleep(10);
        if (WaitNamedPipeW(name, 10))          break;  // 管道出现了
        if (GetLastError() != ERROR_FILE_NOT_FOUND) break;  // 别的错误，认栽
        budget_ms -= 10;
    } while (budget_ms > 0);

    HANDLE h = CreateFileW(name,
                           GENERIC_READ | GENERIC_WRITE,
                           0, NULL,                    // 独占、默认安全描述符
                           OPEN_EXISTING,
                           FILE_ATTRIBUTE_NORMAL,
                           r15);                       // 第 7 参走寄存器，按惯例应为 NULL
    self->pipe = h;                                    // [r14+8]
    return h != INVALID_HANDLE_VALUE;                  // setne bl
}
```

几个值得注意的手艺。每轮先睡 10 毫秒再探测，`WaitNamedPipeW` 自己的超时也是 10——双保险，纯粹的忙等避免者写法。错误处理只认 `ERROR_FILE_NOT_FOUND`（2，管道还没建）继续等，别的错误立即放弃去连一次——很老练：管道被独占（ERROR_PIPE_BUSY）它反而直接 CreateFile 碰运气。esi 预算从 main 开头那句 `mov esi, r14d`（0）起算的话这段是死代码，所以初值必然在调用前被装填，具体多少毫秒我没有单验，留个记号。

名字这一侧的物证清单：文件里有 `\\.\pipe\` 前缀（UTF-16）、ASCII 碎片 `-trainer`（两处）、协议串 `{CMD}_`、`{CMD}_ChangeHotkey`、`TRAINER_ID`、配置路径 `\TrainerSettings.ini` 和 `\info.ini`——配合导入表里的 `GetPrivateProfileStringW` / `WritePrivateProfileStringW`，热键自定义存 INI 这条线静态就闭环了。唯独完整管道名零命中。

而动态那边，进程活着的时候 `FLiNGTrainerNamedPipe_<pid>` 真实存在，进程一死它就消失。有个细节很多人会漏：全文件没有 `CreateNamedPipe`（ASCII/UTF-16 双 -1），客户端代码只 Wait + CreateFile，可管道确实在本进程生命周期内存在、又没有子进程——**服务端八成在托管层**，System.IO.Pipes 走 CLR 内部 P/Invoke 建管道，宿主 EXE 的导入表照旧看不见。推断，但动静证据咬合得很紧。

## 8. 资源区开箱：第二块 PE 与 7.8 熵的黑盒

资源树里最有料的是 `/REMOTE/250`——142,848 字节的**内嵌 x64 PE**：

```
入口点   : 0x3730
时间戳   : 2024-03-31（比宿主老两年，现成组件拼装的痕迹）
导入     : KERNEL32 ×95，外加 WINMM!timeGetTime
           里面有 SuspendThread / ResumeThread / GetThreadContext /
           SetThreadContext / OpenThread / CreateToolhelp32Snapshot
字符串   : "TrSpeedHack_x64.dll"、"Trainer Speedhack Library"
导出     : num_names = 0（序号导出，或导出表形同虚设）
```

`timeGetTime` 加上线程快照和挂起/恢复——变速齿轮的身份不用自证了，这套 API 组合就是"遍历线程 → 挂起 → 换时钟 → 恢复"的教科书形状。宿主程序自己的导入表里连一个线程上下文 API 都没有，加速能力整个藏在资源区的第二块 PE 里——又一个"导入表不等于能力"的实锤。

旁边 `/REMOTE/246` 只有 4 字节：`0xFFFFFFFF`，像开关或版本标记。`/COVER` 73,628 字节是封面图。两段 WAVE 资源对上导入表里唯一的 `WINMM!PlaySoundW`——按热键有音效，静态侧的自洽小闭环。

真正打不开的是 `/UI/101`：198,656 字节，**熵 ≈ 7.8**（满分 8）。这个熵值意味着数据几乎不可压缩——要么是压缩包，要么是加密数据。简单单字节 XOR 试了没开门。它是什么？`mscoree!CLRCreateInstance` 的导入、满文件找不到的管道名、动态侧看到的整套 WPF 栈，三条线索指向同一个答案：**托管 UI 程序集大概率就封在这个黑盒里**。解密算法在原生代码里，26 处 GetProcAddress 的簇里可能就有它的一角——这是全样本最值得下一期深挖的地方。

## 9. 23 条 CE 脚本：修改器的业务代码

修改器真正的"功能"不是那两万多行原生代码，是 23 条 Cheat Engine 风格的自动汇编脚本，明文躺在文件里。脚本引擎的分发点也找到了：`aobscanmodule` 关键字（UTF-16，RVA 0xDC0F8）全文件唯一一处引用——

```asm
0x140079FEC:  lea   rdx, [rip + 0x62105]   ; → 0xDC0F8 = L"aobscanmodule"
0x140079FF3:  lea   rcx, [rsp + 0xc0]
0x140079FFB:  call  0x140084e50             ; 关键字分发：这是哪种指令？
```

也就是说解析器是这台修改器自己带的，不需要外面的 Cheat Engine。CE 脚本的套路三句话说完：`aobscanmodule` 在目标进程里按字节模式扫描定位代码 → `alloc` 开一块可执行洞，把原指令搬进去补完私货，原址改写成 `jmp` 进洞 → `[DISABLE]` 把原字节一个不差写回去。看三条代表作。

**第一条，锁血。** 扫描串 `48 85 C9 48 0F 44 D7 C5 FA 10 32 A8 01 0F 85` 拆开是：`test rcx,rcx; cmove rdx,rdi; vmovss xmm0,[rdx]; test al,1; jnz …`——一段"玩家指针判空后取浮点血量"的典型形状。钩子只有 7 字节：`jmp newmem; nop 2`。洞里的私货：

```asm
newmem:
  test  rcx, rcx
  je    code                       ; 空指针不碰
  push  rbx
  mov   rbx, [rcx+sr1]             ; sr1 是脚本里定义的偏移符号
  mov   [player_check], rbx        ; 把玩家对象亮给 UI 层
  mov   [player], rcx
  mov   ebx, [max_health_f]        ; 记录真实上限
  cmp   ebx, 0
  jle   @f
  mov   [rdx+04], ebx              ; 写回上限
@@:
  cmp   [godmode], 1
  je    @f                         ; 无敌开关开着 → 直接加血
  cmp   [health], 1
  jne   skip_health                ; 两个开关都关 → 原样放行
@@:
  fld   [rdx+04]                   ; 取上限
  fadd  [bonus_health]             ; + 10000.0（dd (float)10000）
  fstp  [rdx]                      ; 写回当前血
skip_health:
  pop   rbx
code:
  test  rcx, rcx                   ; 原指令原样执行
  cmove rdx, rdi
  jmp   return
[DISABLE]
aobplayer: db 48 85 C9 48 0F 44 D7  ; 逐字节回写，一个不差
```

`registersymbol(godmode health max_health_f player …)` 把这些开关注册成全局符号——UI 那 23 个热键按下去，写的就是这些地址。锁血的实现就是这么朴素：血量结构上浮一万点浮点。

**第二条，技能无冷却。** 扫描串 `48 0F 44 C8 48 39 4F 68 0F 86 * * 00 00` = `cmove rcx,rax; cmp [rdi+68],rcx; jbe …`——比较冷却计数和阈值决定跳不跳。洞里三行手术：

```asm
code:
  cmove  rcx, rax            ; 原条件搬移照做
  mov    qword ptr [rdi+68], 0   ; 把 [rdi+68] 清零 ← 手术就这一刀
  cmp    [rdi+68], rcx       ; 重做比较，标志位照样生效
  jmp    return
[DISABLE]
aobskillcd: db 48 0F 44 C8 48 39 4F 68   ; 8 字节原样还
```

冷却字段每次比较前被清零，`jbe` 后面的代码永远认为"冷却完毕"。注意它清零之后还把原比较重做一遍——标志位语义不破坏，后面依赖 ZF 的分支不会乱。这种"改数据不改控制流"的手法比硬跳转体面得多。

**第三条，潜行二补丁。** 最短的一条，连洞都不开：

```asm
[ENABLE]
aobscanmodule(aobstealthmode, ACShadows.exe,
  0F 85 * * 00 00 * 02 00 00 00 * 80 * * * 00 0F 84 * * 00 00)
aobstealthmode+11:
  db 90 E9              ; 原来是 0F 84（je rel32）
[DISABLE]
aobstealthmode+11:
  db 0F 84              ; 写回
```

为什么两个字节就够？x64 里 `0F 84 cd` 是 6 字节的 je rel32，`E9 cd` 是 5 字节的 jmp rel32，位移各占 4 字节。把前两字节 `0F 84` 换成 `90 E9`——`90` 是 1 字节 nop，`E9` 接过原本那 4 字节位移——总长度 1+5 = 6，位移一个没动，落点和原 je 完全相同，只是从"条件跳"变成"无条件跳"。等长换芯，后面的指令一个字节都不用挪，`[DISABLE]` 写回两个字节就完整复原。这是补丁界最经典的小手术之一，第一次见的人会觉得像魔术。

顺带一提，文件名的"23"、扫描出的 `[ENABLE]` 块数（23 个）、动态看到的窗口标题"刺客信条：影 v1.0-v1.1.8 **二十三项**修改器"，三方对上——`ACShadows.exe` 这个模块名也在 23 条脚本里重复出现，和游戏进程名对齐。

## 10. 动态 12 秒：把它关进玻璃箱

静态话讲完，上真家伙。第一次直接起进程，`WinError 740`——清单要管理员权限，拒绝访问。补上提权重跑，这次起来了。

监控脚本逐秒采样，12 秒窗口里看到的：

```
窗口标题 : 刺客信条：影 v1.0-v1.1.8 二十三项修改器   ← 中文 WPF 窗口，自报家门
栈       : clr.dll / clrjit / mscorlib.ni.dll /
           PresentationFramework.ni.dll / mscoree      ← .NET + WPF 实锤
           （还有 GAC 里的 UIAutomation、zh-Hans 资源）
t1 快照  : 线程 28、句柄 738、DLL 141、RSS 114.5 MB、CPU 14.3%
命名管道 : FLiNGTrainerNamedPipe_<pid> 存在；进程退出后消失
子进程   : 无
新文件   : 可执行目录与 %TEMP% 均无新增（INI 只读没写）
加载的网络栈 : winhttp / ws2_32 / schannel / secur32   ← 静态导入表里全没有！
网络连接 : 2 × ESTABLISHED，IPv6 :443
           → 2606:4700:20::ac43:491a  （2606:4700::/32 = Cloudflare 段）
```

几个点值得停一停。第一，`clr.dll` 和 `PresentationFramework.ni.dll` 的出现，把第 3 节静态侧的推断（`CLRCreateInstance` 导入 + `CoInitializeEx(APARTMENT)` = WPF）钉成了事实——UI 是 .NET 写的，中文资源包都在。第二，管道名 `FLiNGTrainerNamedPipe_<pid>` 带进程号后缀，进一步解释了为什么文件里搜不到全名：**前缀、`NamedPipe`、pid 三段是运行时拼的**。第三，全程没有子进程、没有新文件，把"下载器/投放器"的怀疑洗掉一半——它没往硬盘上写任何东西。

插曲也记录一下：第一版监控脚本在 GBK 控制台前炸了个 `UnicodeEncodeError`，残留了一个没监控到的修改器进程，后来手动清掉，用户的《刺客信条：影》进程从头到尾没被碰过。这台机器的控制台是 GBK，Python 打中文必炸，后面所有输出都改成先写 UTF-8 文件再读——分析环境本身也是环境，Wine 探测那段代码看到这场景大概会心一笑。

## 11. 当面对质：静态零网络 vs 两条 TLS

现在把两套证据摆上同一张桌子。

**静态侧的证词：** 9 个导入 DLL 里没有任何 winhttp、wininet、ws2_32；`http://`、`https://`、`winhttp`、`ws2_32` 四个串在文件里 ASCII、UTF-16 双编码全部 -1；144 个导入函数里没有一个与网络有关。结论：**这个进程理论上没有联网能力**。

**动态侧的证词：** 进程起来之后，`winhttp.dll`、`ws2_32.dll`、`schannel.dll`、`secur32.dll` 四个 DLL 进了它的地址空间，两条到 `2606:4700:20::ac43:491a` 的 443 端口 ESTABLISHED 连接挂满全程——那是 Cloudflare 的 IPv6 段（低 32 位 ac43:491a 对应的 A 记录落在 172.67.73.26 一带）。结论：**它不仅联网，还是一条 TLS 加密长连接**。

谁在说谎？都没说谎，这正是本期最想讲的一课：**静态导入表只登记"编译期就确定要链接的 API"，它从来不是运行时能力的完整清单**。这台修改器的网络能力走的是暗道——最可能的路径是托管层：.NET 代码里 `HttpClient` 一调，CLR 内部把 winhttp/ws2_32/schannel 一路拉起来，宿主 EXE 的导入表从头到尾干干净净。第 6 节的三条暗道（GetProcAddress、CLR、加密资源），这里是 CLR 那条道的现场直播。顺带，静态表里也没有任何网络字符串——因为托管程序集封在熵 7.8 的 `/UI/101` 里，域名自然也搜不到。

连接到 Cloudflare 干什么？**不知道，这里必须诚实**：TLS 握手里的 SNI 和 HTTP 层的域名我都没抓，看到的只有 IP 和端口。Cloudflare 段上挂的服务成千上万，FLiNG 用它做更新检查、广告位还是配置下发都有可能——按"观察到但未归因"记录：**观察 = 两条到 Cloudflare IPv6 的 443 长连接；归因 = 无**。要坐实域名，下一期得上中间人解密或内存里翻 SNI，这是作业不是结论。

这组矛盾的实践意义就一句话：**做威胁评估，静态零网络导入可以放行一半，动态长连接必须问清楚另一半**。两边各信一半，才是动静结合的正确姿势。

## 12. 没解开的谜，和留给下一期的作业

一期节目不可能把 1.6 MB 吃干抹净，摊开留白清单反而比硬凑结论体面：

1. **域名没归因。** 两条 Cloudflare 连接背后是谁，需要 TLS 层的动静结合（SNI 抓取或内存 dump），本期只有 IP 级观察。
2. **`/UI/101` 黑盒没开。** 熵 7.8、198 KB，托管 UI 程序集和域名字符串大概率都在里面。单字节 XOR 没开门，得去找真正的解密例程——大概率就在 26 处 GetProcAddress 的某一簇附近。
3. **`0x140034720` / `0x140034a50` 两个初始化函数没逐行展开。** Wine 与 `retry-non-windows` 的分流语义目前是推断级，`ecx = 0x65` 的含义未确证，5000 阈值计的是什么没盯到。
4. **线程入口 0x328A0 的后半截没追完。** main 建的那根线程里干了什么，只看了开头五条指令。
5. **管道服务端在托管层是推断。** 证据链（无子进程 + 无 CreateNamedPipe 导入 + 管道随进程生死）很紧，但没做托管堆的字符串提取来直接验证。
6. **3DMGAME 与 FLiNG 的打包关系。** 谁重编译了谁，静态证据只能证明两个商标共存于同一份版本资源。

最后照例是风险提示。这个样本：未签名、来自盗版站、自带管理员清单、内嵌加密黑盒、运行时往 Cloudflare 挂 TLS——恶意证据一条都没抓到（没有落盘、没有子进程、没有注入动作），但信任面就是这么大的东西，双击之前值得三思。360 报毒可能是误报（修改器的行为特征和木马高度重合），也可能不是——在你能独立验证它之前，这两者没有区别。

方法论层面这期沉淀下来的就三条：**静态定骨架，动态定行为，动静对不上的地方才是真发现**。26 处 GetProcAddress 是骨架，两条 TLS 是行为，中间那道"导入表里零网络"的裂缝就是全篇最有信息量的现场。工具链没什么神秘的：`py -m pip install pefile capstone psutil`，一个反汇编循环加几张 UTF-8 报告文件，没有 Ghidra 也能把 1.6 MB 拆到这个颗粒度——过程中我还踩了忘加 ImageBase 查 IAT 全军覆没、GBK 控制台炸中文、`python` 是坏 stub 只能用 `py` 启动器这几个坑，全都值得写进下一期的工具篇。

（本文所有地址均为 RVA/ImageBase 0x140000000 下的虚拟地址；标"推断"处为证据链支撑但未经直接验证的判断；样本 SHA256 见第 1 节，如需复现分析请先核对指纹。）
