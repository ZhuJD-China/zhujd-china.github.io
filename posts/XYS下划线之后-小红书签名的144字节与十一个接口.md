浏览器打开小红书，随手点开一条笔记，DevTools 的 Network 面板里会多出两个没见过的头：`x-s` 和 `x-s-common`。前者三百多字符，以 `XYS_` 开头，看着像乱码，可它一缺席服务端就回 406。

我从这段字符串开始拆，一路拆到里面那个 144 字节的结构体，又顺着它把十一个接口的参数形状一个个试了出来。文中数字都是跑脚本量的，不是照着源码数格子数的——手数必错，后面有实例。

全程只碰只读接口，没发过笔记，没点过赞，没留过评论。这是技术拆解，不是调用指南。

## 1. 起点是一次 406

起因很朴素，想批量拿几条公开笔记的正文和评论。F12，搜个关键词，复制一条请求出来 cURL：

```http
GET /api/sns/web/v1/user_posted?num=20&cursor=&user_id=64...&image_formats=jpg,webp,avif
x-s: XYS_2UQhPsHCH0c1PUhMHjIj2erjwjQh...
x-s-common: 2UQh...
x-rap-param: (GET 没有)
cookie: a1=...; web_session=...
```

第三行那个 `image_formats=jpg,webp,avif`，逗号是字面量（第 11 节整篇就讲这一个字符）。

照抄着发出去，服务端回：

```text
HTTP 406 Not Acceptable
{"code": -1}
```

body 恒定是这个。**`code: -1` 不含任何信息量**，它只说验签没过，不说哪一步没过。没有错误位置可看，后面的排查只能是自己把每一步逐个对一遍——第 11 节是这么破的。

先把三个头分清楚，后面处处要用：**`x-s` 锁这一条请求**，路径、参数、时间都在里面；**`x-s-common` 锁这个人**，cookie 指纹和设备信息；**`x-rap-param` 锁请求体本身**。三者各管一摊，缺一个都不行。

| 头 | 本例长度 | 内容 | 是否每次都变 |
|---|---|---|---|
| `x-s` | 364 | `XYS_` 开头的信封 | 是 |
| `x-s-common` | 1292 | `2UQh` 开头 | 是 |
| `x-rap-param` | 变长 | body 的压缩加密包 | 是 |

## 2. XYS_ 剥开是个 JSON

`XYS_` 后面那段不是标准 Base64。先把字符按另一张字母表换回标准表，再 `b64decode`，得到一个 JSON：

```text
XYS_ 2UQhPsHC...
       │
       └─ 按自定义字母表换回标准表，再 b64decode
          ↓
{"x0":"4.3.5","x1":"xhs-pc-web","x2":"Windows","x3":"mns0301_...","x4":"object"}
```

实测各段长度：

```text
full x-s length          : 364
x-s prefix               : 'XYS_'
encoded body length      : 360  (pad chars: 1)
json length              : 269
x3 length                : 200
x3 prefix                : 'mns0301_'
x3 encoded part length   : 192
x3 decoded raw length    : 144 bytes
```

4 加 360 等于 364（前缀 `XYS_` 占 4 个字符）。JSON 是 269 字节（269 除 3 余 2，所以带一个 `=`），其中 `x3` 占 200，去掉 `mns0301_` 剩 192 字符，解出来 144 字节。这几个数是解码脚本逐字段打出来的，不是对着源码数出来的——引号和填充符最容易数错。

`x0` 到 `x4` 里，`x0` 是 SDK 版本，`x1` 是 appId，`x2` 是平台，`x4` 是个类型标记（值恒为 `object`，我没见过它变），全是明文常量。**真正干活的只有 `x3`**，后面十几节讲的全是它。

`mns0301_` 的形状像 `<算法代号>_<版本号>`：`mns` 大概是算法代号，`0301` 看着是版本号。这是从命名惯例推的，我手上没有第二个版本的样本可对照。如果推测成立，服务端看到前缀就知道该拿哪套解法去验后面那 144 字节，版本一变旧实现直接失效。签名方案得挂在常量里随时能改，道理就在这。

有个小细节能拿来验自己的实现：外层 JSON 永远以 `{` 开头，`{` 的前六位是 `011110`，十进制 30，查自定义字母表第 30 位是 `2`。所以 **`XYS_` 之后的第一个字符必然是 `2`**。`x-s-common` 没有前缀、同样以 `{` 打头，于是它整段以 `2UQ` 开头；`XYW_` 是例外，它走标准字母表，首字符是 `e`。看一眼首字符就知道现在发的是哪套信封，不必先解码。你的实现要是连这个都对不上，前面就白忙了。

## 3. 三套字母表

项目里躺着三张 Base64 字母表：

```text
标准 : ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/
外层 : ZmserbBoHQtNP+wOcza/LpngG8yJq42KWYj0DSfdikx3VT16IlUAFM97hECvuRX5
x3   : MfgqrsbcyzPQRStuvC7mn501HIJBo2DEFTKdeNOwxWXYZap89+/A4UVLhijkl63G
```

三张都是 64 字符，互不相同（换错一张，解码出来的 JSON 立刻不成形）。要紧的是，**这不是一种新编码，只是换了一张表**。编码流程就是标准 `b64encode`，然后按表做字符替换：

```python
def encode(self, data_to_encode):
    data_bytes = data_to_encode.encode("utf-8") if isinstance(data_to_encode, str) else bytes(data_to_encode)
    standard_encoded_string = base64.b64encode(data_bytes).decode("utf-8")
    return standard_encoded_string.translate(self._custom_encode_table)   # 就这一行
```

`str.maketrans` 建一张 64 到 64 的映射，`translate` 扫一遍（线性开销，跟 base64 本身同量级），解码反着来。这层东西的防御价值约等于零——它唯一的作用是让「把字符串贴进在线 base64 解一下」这种最低成本的探查失效，把随手试试的人挡在门外。真要查的人，三张表 dump 出来就完了。

**两张表里都有 `+/`，但没有 `=`**。外层因为 JSON 长度不是 3 的倍数会带一个填充符，而那个字符不在表里，原样透传；`x3` 那层 144 字节正好是 3 的倍数，从来不带 `=`（所以那层的 `decode` 不用先补 `=`，少了这个坑）。

## 4. content_string：一切的源头

144 字节里最重要的两格是两个 MD5，输入叫 `content_string`（对应后面那张表里偏移 32 的长度和偏移 36 的指纹）。整套算法从它开始，它也最容易出错：

```python
def _build_content_string(self, method, uri, payload=None):
    payload = payload or {}

    if method.upper() == "POST":
        # POST：路径拼紧凑 JSON，无空格，中文不转义
        return uri + json.dumps(payload, separators=(",", ":"), ensure_ascii=False)
    else:
        if not payload:
            return uri
        params = []
        for key, value in payload.items():
            if isinstance(value, list | tuple):
                value_str = ",".join(str(v) for v in value)
            elif value is not None:
                value_str = str(value)
            else:
                value_str = ""

            encoded_value = urllib.parse.quote(value_str, safe=",")   # ← 逗号
            params.append(f"{key}={encoded_value}")

        return f"{uri}?{'&'.join(params)}"

def _generate_d_value(self, content: str) -> str:
    return hashlib.md5(content.encode("utf-8")).hexdigest()
```

GET 用 `safe=","`，逗号保持字面量，`jpg,webp,avif` 编完还是 `jpg,webp,avif`。这是整套方案里最反直觉的一条：**签名串和最终发出去的 URL，编码规则不是一回事**。签名按 `quote(safe=",")` 算，URL 交给 `requests` 会被 `quote_plus` 再编一遍，两者必须手工对齐。第 11 节的 406 就栽在这。

**参数顺序就是字典的插入顺序，没有排序**（Python 3.7 起 dict 保序，换别的语言实现得自己记顺序）。签名时用的顺序必须和实际发出的完全一致，字典一旦重排签名就废了，而报错还是那个没信息量的 406。

POST 是无分隔符紧凑 JSON，`ensure_ascii=False`，中文直接以 UTF-8 原样进 MD5。这里也踩过坑——对照浏览器抓包时，body 里多一个空格、或者把中文转成 `\uXXXX`，MD5 就对不上，而两边的字符串用肉眼扫几乎看不出区别。

实际产出：

```text
GET  : /api/sns/web/v1/user_posted?num=10&cursor=&user_id=5ff0...&image_formats=jpg,webp,avif
       byte length = 103
       d = 89df9b09a3d78a8627cb4e78685334de

POST : /api/sns/web/v1/user_posted{"keyword":"美食","page":1}
```

## 5. 144 字节，逐格摊开

这是全文的核心。144 字节，14 个字段，全部小端序：

```text
 off  len  字段                                取值/含义
----------------------------------------------------------------------------
   0    4  版本标识                            [121, 104, 96, 41]   (实现里叫 VERSION_BYTES)
   4    4  随机种子 seed (LE u32)               每次生成，参与下面两处 XOR
   8    8  x-t 毫秒时间戳 (LE u64)              请求头里那个 x-t
  16    8  伪 page-load 时间 (LE u64)           x-t 再往前推 10~50 秒
  24    4  sequence (LE u32)                    15~50 随机
  28    4  window props 长度 (LE u32)            1000~1200 随机
  32    4  content_string 字节长 (LE u32)        本例 103
  36    8  MD5(d) 的前 8 字节 ^ seed             路径指纹
  44    1  a1 长度 (u8)                          52
  45   52  a1（不足补 \x00）                      cookie 里的设备标识
  97    1  appId 长度 (u8)                       10
  98   10  appId（不足补 \x00）                   xhs-pc-web
 108   16  环境标志位 (1 + 14)                   1, seed^ENV_TABLE[0], ...
 124   20  a3 前缀 + 自定义哈希 ^ seed             [2, 97, 51, 16] + 16 字节
----------------------------------------------------------------------------
 总长 144（与 PAYLOAD_LENGTH 一致）
```

表是脚本重建 buffer、按 offset 打印出来的，不是照源码数格子数出来的。

构造代码：

```python
payload = list(self.config.VERSION_BYTES)                 # 4
payload.extend(self._int_to_le_bytes(seed, 4))            # 4

ts_bytes = self._int_to_le_bytes(int(timestamp * 1000), 8)
payload.extend(ts_bytes)                                  # 8

effective_ts_ms = int((timestamp - time_offset) * 1000)   # time_offset ∈ [10, 50]
payload.extend(self._int_to_le_bytes(effective_ts_ms, 8)) # 8
payload.extend(self._int_to_le_bytes(sequence_value, 4))  # 4
payload.extend(self._int_to_le_bytes(window_props_length, 4))  # 4
payload.extend(self._int_to_le_bytes(len(string_param.encode()), 4))  # 4

md5_bytes = bytes.fromhex(hex_parameter)
payload.extend([md5_bytes[i] ^ seed_byte for i in range(8)])   # 8

a1_bytes = a1_value.encode()[:52].ljust(52, b"\x00")
payload.append(len(a1_bytes)); payload.extend(a1_bytes)    # 1 + 52

app_bytes = app_identifier.encode()[:10].ljust(10, b"\x00")
payload.append(len(app_bytes)); payload.extend(app_bytes)  # 1 + 10

part11 = [1, seed_byte ^ self.config.ENV_TABLE[0]]
part11 += [self.config.ENV_TABLE[i] ^ self.config.ENV_CHECKS_DEFAULT[i] for i in range(1, 15)]
payload.extend(part11)                                     # 16

payload.extend(self.config.A3_PREFIX + [b ^ seed_byte for b in self._custom_hash_v2(ts_bytes + md5_path_bytes)])
                                                           # 4 + 16
```

`a1` 那 52 字节是全表最大的一格（占整个结构体三分之一强），右补零。实际上 cookie 里的 a1 恒定 52 字符，所以补零那个分支永远不会触发——纯防御性代码，留着它是因为改了也没好处。

长度字段采用前缀式自描述：先给长度再给内容。好处是解析器不用靠固定偏移硬切，坏处是长度一旦被改后面整片错位，而 `a1` 的长度写死在偏移 44，动不得。

偏移 16 那个「伪 page-load 时间」是 `x-t` 再往前推 10 到 50 秒，模拟的是页面在十几秒前加载过。这暗示服务端曾经拿它和会话建立时间做过比对——如果每次都恰好等于 `x-t`，就说明没有真实页面，每次请求都是当场造的，所以这里必须有偏移。同理 `sequence` 和 `window props 长度` 是两格纯随机会话量，代码上能确定的只有它们不依赖任何输入，不进 MD5 也不进 content_string。至于服务端拿它们做别的什么，客户端这一侧看不出来。

变长字段之间没有 padding，靠前缀长度切分，整个结构体紧凑拼接一个字节不多。**所以 144 这个长度是算出来的**：4+4+8+8+4+4+4+8+1+52+1+10+16+20，正好 144（其中偏移 44 和 97 那两个 1 是长度字段本身，最容易漏数）。

## 6. 两份 MD5，两处异或

组好的 144 字节先过两道异或，再编码。

第一道是整片异或，一把 144 字节的固定密钥，逐字节来：

```python
def xor_transform_array(self, source_integers):
    result_bytes = bytearray(len(source_integers))
    key_bytes = bytes.fromhex(self.config.HEX_KEY)   # 恰好 144 字节
    key_length = len(key_bytes)

    for index in range(len(source_integers)):
        if index < key_length:
            result_bytes[index] = (source_integers[index] ^ key_bytes[index]) & 0xFF
        else:
            result_bytes[index] = source_integers[index] & 0xFF   # 越过密钥的部分原样保留

    return result_bytes
```

密钥长度恰好等于 payload 长度，所以 **`else` 分支是死代码**。看着像从更早的实现留下来的兼容逻辑——那时密钥可能短于结构体，尾巴上几个字节不加密；结构体加长、密钥也跟着加长了，这段没删（推测，没有更早的版本可对照）。逆向里经常见到这种痕迹，它本身就是一条时间线索——说明这个格式被扩展过。

第二道只覆盖两格。偏移 36 的 8 字节是 `MD5(d)` 前 8 字节再异或 `seed`，偏移 128 起的 16 字节（前面 124 到 127 是 `a3` 前缀）是自定义哈希的输出再异或 `seed`。

第一道已经用了固定密钥，这里为什么还要再异或一次种子？因为固定密钥意味着只要两个请求的原始结构体相同，密文就相同。而 `seed` 每次随机会话都不同，把它混进这两格，就能保证即使路径、时间、a1 全一样，最终 144 字节也不一样（第 9 节会量化这个效果）。

两个 MD5 的分工：

```python
content_string = self._build_content_string(method, uri, payload)
d_value = self._generate_d_value(content_string)                    # MD5(路径+参数)
m_value = d_value if method == "GET" else hashlib.md5(uri.encode()).hexdigest()  # MD5(仅路径)

payload_array = self.crypto_processor.build_payload_array(
    d_value,   # → 偏移 36
    m_value,   # → 偏移 124 的 a3 输入
    a1_value, xsec_appid, content_string, timestamp, sign_state=sign_state,
)
```

**GET 时两个槽位拿同一个 `d`（所以那两格内容一致）；POST 时第一个是 `MD5(路径 + 紧凑 JSON)`，第二个退回成 `MD5(仅路径)`。** 结构体里因此同时记了整条请求的指纹和这个端点的指纹——服务端验 POST 时，第二个 MD5 让它不读 body 也能先确认请求打在预期路径上，再回头校验 body。两个都对，请求才算完整。

## 7. a3 那一段哈希

偏移 124 起是 `a3`。前 4 字节是硬编码前缀 `[2, 97, 51, 16]`，ASCII 正好是 `\x02a3\x10`，`a3` 这个名字就来自这里。后面 16 字节是 `_custom_hash_v2(ts_bytes + md5_path_bytes)` 的输出，再逐字节异或 `seed`。

这个函数不是 MD5 也不是 SHA，是自己写的一套带初值、分组的哈希：

```python
def _custom_hash_v2(self, input_bytes):
    s0, s1, s2, s3 = self.config.HASH_IV
    length = len(input_bytes)

    s0 ^= length
    s1 ^= length << 8
    s2 ^= length << 16
    s3 ^= length << 24

    for i in range(length // 8):
        v0, v1 = struct.unpack("<II", bytes(input_bytes[i * 8 : (i + 1) * 8]))
        ...   # 32 位字节序解包，逐块轮转异或
```

输入是 `ts_bytes` 加 `md5_path_bytes`，8 加 16 等于 24 字节，正好三个 8 字节块，输出固定 16 字节。

特征很明显：先把总长按四种偏移异或进四个初值（`length`、`length << 8`、`<< 16`、`<< 24`），这是 MurmurHash 系的常见起手式，然后按 8 字节分组、小端解包、做 32 位旋转异或。它自研、刻意不撞现成库——你拿 MD5 或 SHA 去算，结果永远对不上。反过来，在逆向里认出「这不是任何标准算法」，本身就说明这段代码被刻意选过。

同族的还有 `x-s-common` 里的 `CRC32.crc32_js_int`，以及配置里那个用于 gid 的 8 字节 DES 密钥，同样是明文硬编码。这些非标准原语合起来构成一层，让任何依赖哈希特征匹配的通用方法全部落空。

## 8. x-s-common 管的是人

`x-s` 管单条请求，`x-s-common` 管人。它更长，1292 字符，结构反而简单：一个 JSON，用外层那张字母表编一次。

```python
class XsCommonSigner:
    def sign(self, cookie_dict):
        a1_value = cookie_dict["a1"]
        fingerprint = self._fp_generator.generate(cookies=cookie_dict, user_agent=...)
        b1 = self._fp_generator.generate_b1(fingerprint)

        x9 = CRC32.crc32_js_int(b1)

        sign_struct = dict(self.config.SIGNATURE_XSCOMMON_TEMPLATE)
        sign_struct["x5"] = a1_value     # 设备 id
        sign_struct["x8"] = b1           # 指纹摘要
        sign_struct["x9"] = x9           # b1 的 CRC32

        sign_json = json.dumps(sign_struct, separators=(",", ":"), ensure_ascii=False)
        return self._encoder.encode(sign_json)
```

模板长这样：

```json
{"s0":5,"s1":"","x0":"1","x1":"4.3.5","x2":"Windows","x3":"xhs-pc-web",
 "x4":"4.86.0","x5":"","x6":"","x7":"","x8":"","x9":-596800761,
 "x10":0,"x11":"normal"}
```

**十三个字段里只有三个是活的**（其余十个换页也不动）：`x5` 是 a1，`x8` 是指纹，`x9` 是 `x8` 的 CRC32。`x9` 是弱校验，CRC32 公开且碰撞容易，它显然不是防线；能确定的是单独改 `x8` 一个字段会被它发现。服务端究竟拿 `x9` 做什么，客户端这侧看不出来，我也不打算编一个理由出来。

`x8` 从整个 cookie 集合推出（配套一个明文写在配置里的 `B1_SECRET_KEY`），所以换 cookie 就得重算 `x-s-common`，换 UA 也一样——它必须和 `x-s` 用同一套 cookie，这就是两个头不能分别来自两个会话的原因（分属两个会话的头一起发，指纹和签名对不上）。

## 9. 签名不能复用

结构体里有三处随机量：偏移 4 的 seed、偏移 24 的 sequence、偏移 28 的 window props 长度，外加偏移 16 的时间偏移。同一个请求签两次，结果必然不同。

拿同一输入（同一 cookie、同一毫秒、同一参数）签了 12 次，量了与基准的公共前缀：

```text
identical input, identical timestamp, 12 signatures
  all equal          : False
  lengths            : [364]
  common prefix min  : 92
  common prefix max  : 93
  sample prefixes    : [92, 92, 92, 92, 92, 92, 93, 92, 92, 92, 92, 92]
```

长度恒定 364，因为长度由 JSON 结构决定，随机只影响内容不影响长度——**长度本身不是熵的来源**。前 92 到 93 字符稳定，第 93 位附近开始分叉，稳定的部分是 `XYS_` 加外层 Base64 里由 `x0`、`x1`、`x2` 和 `x3` 前段决定的位。12 次全部不相等，完全相同的输入产生了完全不同的输出。

由此推出三条，条条都踩过：

- **签名不能缓存。** 没法先算好等着发，每回都得重算。
- **签名不能做 diff。** 两个请求的 `x-s` 不同不能说明参数变过——它每次都不相同，拿它对差异只会越查越远。
- **每次都要带当前时间戳和当前 cookie。** 时间一过，之前签的全作废。

顺手也量了改参数、改时间戳后的分叉位置：

```text
identical input : 92~93
cursor=abc      : 93
ts+60s          : 92
```

三种改动全部落在同一位置。改动不会让字符串提前或推后分叉，分叉点只由 JSON 的字节偏移决定，跟输入内容无关。这反过来又是个可用的自检：你的实现要是改个参数分叉点跑到 60 或 120，前面的编码链已经错了。

## 10. body 也要装袋

GET 没有它，POST 才有。十一个接口里只有两个带 body 的需要 `x-rap-param`：`search_notes` 和 `note_feed`。

它把请求体也打包加密，防止签名合法、body 却在签名之后被换过。流程是 `api path + payload` 压缩、加密、包一层协议版本（`XRAP_SDK_VERSION = 10300`）、Base64。端点配置上用一个布尔标记（第四个位置，`True` 就是带 body 的那两个）：

```python
"search_notes": (SO,  "POST", "/api/sns/web/v2/search/notes", True,  MAIN),
"note_feed":    (EDITH, "POST", "/api/sns/web/v1/feed",       True,  MAIN),
"comment_page": (EDITH, "GET",  "/api/sns/web/v2/comment/page", False, MAIN),
```

实测的规律是，带 `x-rap-param` 的都是 POST 且走 MAIN 签名，走 creator 的两个 POST 反而不带，它们另有一套自己的 body 保护方式。

**漏发这个头不报错，只是静默返回空数据**——比 406 还难查（请求 200、`success: false`、`payload: []`，三个都不是错误的形态）。你调参的时候不会怀疑到头字段上，会一直往参数里钻。

## 11. 406 的真凶是一个逗号

回到第 1 节。406 只说验签没过，不说哪里没过，排查的唯一办法是让自己产出的 URL 和签名时算的 content_string 逐字节一致。把两者并排打出来：

```text
签名算的 : ...image_formats=jpg,webp,avif      ← 逗号是字面量（quote(safe=",")）
实际发出 : ...image_formats=jpg%2Cwebp%2Cavif  ← 逗号被 quote_plus 转义成 %2C
```

差一个字符，签名就废。

根因是 `urllib.parse.quote(value, safe=",")` 在签名侧把逗号当字面量，而 `requests` 用 `quote_plus` 在发送侧把逗号转义成 `%2C`。签名算法和 HTTP 库对同一段文本的编码规则不一致，服务端又是拿它收到的 URL 去验的（不是拿你签名时算的那个串），所以必须让发出去的 URL 和签名用的串完全相同。

修法是不把参数交给 `requests` 自动编码，手工按 `quote(safe=",")` 拼出 query string 直接放进 URL（`query_url()` 干的就是这件事）：

```python
def query_url(self, ...) -> str:
    """生成与签名编码器逐字节一致的完整 URL"""
    ...
```

改完之后 406 消失。这条 bug 我记在踩坑表里，因为它是那种看起来百分之百像签名算法错了、实际是 URL 编码顺序错了的典型：**越是去怀疑 MD5、怀疑 XOR 密钥、怀疑字母表，走得越远**。看到 406 直接查编码，别查哈希。

## 12. 两套信封的边界

`XYS_` 不是唯一的，还有 `XYW_`：

```text
XYS_ {"x0":"4.3.5","x1":"xhs-pc-web","x2":"Windows","x3":"mns0301_...","x4":"object"}
XYW_ {"signSvn":"56","signType":"x2","appId":"...","signVersion":"1","payload":"<AES 结果>"}
```

`XYW_` 的 `payload` 是 AES-128-CBC 加密的结果，密钥是配置里硬编码的 16 字节 ASCII 字符串（16 字节正好是 AES-128 的整块密钥）。明文在客户端，任何人打开页面 JS 都拿得到，所以它防的不是有心人，是随手改个参数的脚本。

两套信封的外层编码不同：`XYS_` 是标准 Base64 之后再按自定义字母表换字符，`XYW_` 直接用标准 `b64encode`（第 2 节的首字符判别就建立在这点上）。前者的首字符永远是 `2`，后者永远是 `e`。抓到一条 `x-s` 看这一个字符就够了，不用先解码。

边界按端点路径划，不按域名划：

| 路径 | 签名 | origin / referer |
|---|---|---|
| `/api/sns/web/*` | `XYS_`（main） | `www.xiaohongshu.com` |
| `/web_api/*` | `XYW_`（creator） | `creator.xiaohongshu.com` |

有个反直觉的点：`/web_api/*` 的实际 host 仍然是 `edith.xiaohongshu.com`，只是签名换成 `XYW_`、origin 和 referer 换成 creator 域名。**按域名划分这两套信封会判断错**，真正的分界在端点路径上。

用错的后果是两种完全不同的拒法。主站路径用错签名拿到 406，body 是 `{"code":-1}`，会话没事，修好还能用。创作者路径用错 appId，比如拿引擎自带的 `xhs-pc-web` 发给评论接口，拿到 461/300011「当前账号存在异常」。

第二种我撞上过，后果比第一种严重得多：**会话被打废，重试救不回来**。判断依据是同一 cookie 换个健康端点（`user/me`）立刻 200，说明 cookie 没过期，是这个特定操作触发了风控，唯一解是换 `web_session`。

这就是为什么封装层按路径自动选签名方案、不把 `sign_format` 暴露给调用方。早期版本留过一个参数让调用方自己指定，等于把「把会话打废」的按钮交了出去，后来删掉，签名方案完全由端点配置决定，外部改不了。同样删掉的还有 `UNVERIFIED` 那套「未验证也发出去试试」的开关——一条没人验证过的请求，失败时返回的错误看着和正常错误一模一样，它污染的是你自己的判断。

全部通过真实 cookie 实测。

| 方法 | 接口 | 中文名 | 路径 | 签名 | 说明 |
|---|---|---|---|---|---|
| POST | `search_notes` | 搜笔记 | `/api/sns/web/v2/search/notes` | XYS | 关键词搜笔记，返回标题、作者、点赞数，以及后续都要用的 `xsec_token` |

| GET | `search_recommend` | 搜索联想词 | `/api/sns/web/v1/search/recommend` | XYS | 输入框联想词，返回 `code: 1000` 但 `success: true` |
| POST | `search_topic` | 搜话题 | `/web_api/sns/v1/search/topic` | XYW | 话题标签，返回话题名、链接、浏览量 |
| POST | `search_user` | 搜用户 | `/web_api/sns/v1/search/user_info` | XYW | 用户账号，返回昵称、小红书号、`user_id`、粉丝数 |

| GET | `comment_page` | 一级评论 | `/api/sns/web/v2/comment/page` | XYS | 一级评论，含每条的 `sub_comment_count` 和首屏子回复 |
| GET | `comment_sub_page` | 子评论回复 | `/api/sns/web/v2/comment/sub/page` | XYS | 子回复，用 `root_comment_id` 定位、`sub_comment_cursor` 翻页 |

### 参数形状是摸出来的

这部分没法靠读文档，只能一个个试。几个试错的例子：

`search_topic` 的 body 必须嵌套，拍平成 `{"page":1,"page_size":20}` 直接 400。正确形状是 `{"page": {"page_size": 20, "page": 1}, "keyword": "...", "suggest_topic_request": {}}`——外层还得再挂一个空的 `suggest_topic_request`，它一个字都不传，漏了却报错。

`comment_sub_page` 的参数名是 `root_comment_id`，不是 `top_comment_id`。**名字发错了，服务端不报「参数不存在」，返回的是 `-9109`**，而这个码的字面语义是「id 找不到」。参数名拼错和 id 真的不存在，返回码一样——这是最坑的一种错，你会一直以为自己 id 传错了，反复换 id，怎么换都是 -9109。

子评论翻页必须同时带 `xsec_token` 和 `image_formats`，少任何一个就是 461/300031「当前笔记暂时无法浏览」。注意它和 461/300011 是不同子码：30031 是参数不全被拦，能修；30011 是风控，会废会话。两个都报 461，认错子码会白折腾很久。

`user_posted` 是真·无文档接口，参数只能一个个试。`num`、`cursor`、`user_id`、`image_formats` 里，**`image_formats` 的值必须是字符串 `"jpg,webp,avif"`**，而 `search_notes` 的同名参数是数组。同一个参数名在不同端点类型不同，服务端不校验类型的时候还会静默返回空列表，不报错。

**翻页也各有各的**：一级评论用 data 顶层的 `cursor`，子评论用父评论对象里的 `sub_comment_cursor`（既不是顶层那个，也不是 `""`）。计数字段 `liked_count`、`sub_comment_count` 是字符串 `"87"`、`"4"`，做加法会拼成 `"874"` 而不是 91。

## 14. 错误码

实测撞到过的，按能不能自己修分三类：

| 状态 / 码 | 表现 | 能否自修 | 处置 |
|---|---|---|---|
| `406` `{"code":-1}` | 验签失败 | 能 | 查 URL 编码顺序、查 content_string，别查哈希 |
| `400` | body 形状错 | 能 | 对照抓包改结构，多半是漏了嵌套层 |
| `-9109` | 说找不到 | 一半 | 先确认参数名拼写，再怀疑 id |
| `461/300031` | 当前笔记暂时无法浏览 | 能 | 补 `xsec_token` + `image_formats` |
| `461/300011` | 当前账号存在异常 | 不能 | 会话已废，换 `web_session`，重试无效 |
| `461/471` | 要人解验证码 | 不能 | 停手，别继续刷 |
| 200 + `success:false` | 无数据 | 一半 | 先查 `x-rap-param` 漏没漏，再查参数 |
| `code:1000` + `success:true` | — | — | 正常，不是错误 |

**最后三行最值钱**，因为它们都不会以错误的形态出现（200 加空 payload、`code:1000` 带 `success: true`）。调用层只判 `status_code` 的话，这三种一个都发现不了——而它们恰恰是最常见的失败形态。

## 15. 能复现的才算数

这条我在这个项目里反复强调，也确实栽过跟头——早先我照着路径规律猜过三个端点，没验证就写进了文档，后来全删了。**列表里写了不等于真能用。**

所以现在的规矩是，配置表里只放实测通过的端点，查一个不存在的名字直接抛 `KeyError` 并列出已知键，而不是发一个没人验证过的请求。测试分两层：51 个离线用例覆盖结构构造、归一化和 406 回归（不联网，秒出结果）；14 项端到端验证拿真实 cookie 跑一遍。任何参数名、字段名、返回码，没实测过的不写进文档。

回头看，144 字节那张表本身不难，难的是确认它是对的。**手推偏移表最容易想当然的是引号、填充符和长度字段**，所以每个数我都用脚本重建 buffer、按偏移打印、再和实际签名的解码结果比对一遍。

那十一个接口、每条的必填参数、每个错误码，也是撞出来的不是查出来的。小红书这套接口没有对外文档，`-9109` 这种语义模糊的返回码更是把参数名写错伪装成 id 不存在。没有文档的地方，唯一可信的证据是服务端的回应，而判断它真不真，只能把每个假设都跑一遍。

这套东西会变，`mns0301` 里那个 `0301` 哪天变一变，文中大半代码就失效了。但构造思路大概不会变：明文结构体、随机种子、固定密钥混淆、自定义字母表编码，外加按路径划分的两套信封。看懂一次，下次换版本知道该往哪看。
