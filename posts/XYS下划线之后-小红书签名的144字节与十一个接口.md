这篇写的是一个我们每天在点、但几乎没人停下来掀开的头。

浏览器打开小红书，随便点开一个笔记，DevTools 的 Network 面板里躺着一条 `GET /api/sns/web/v1/feed`。它的请求头比正常网页请求多出三个没见过的字段：`x-s`、`x-s-common`、`x-rap-param`。其中 `x-s` 是一段三百多字符、以 `XYS_` 开头的乱码，没有它服务端直接甩你一脸 `406`。

我从这段乱码开始，一路拆到一个 144 字节的结构体，再顺着它把十一个接口和参数形状一个个试出来。下面所有的数字都是跑出来的，不是推出来的——文中给了脚本，你能自己复现。

先说清楚边界：**全程只碰只读接口**，没有发过一条笔记、点过一个赞、留过一条评论。这篇是技术拆解，不是调用指南；你要拿它做什么，后果自负。

## 1. 起点：一次 406 和三个陌生请求头

一开始的动机很朴素：想批量拿几个公开笔记的正文和评论。打开浏览器，F12，搜关键词，复制一条请求出来 cURL。长这样（头太多，只留关键的）：

```http
GET /api/sns/web/v1/user_posted?num=20&cursor=&user_id=64...&image_formats=jpg,webp,avif
x-s: XYS_2UQhPsHCH0c1PUhMHjIj2erjwjQh...
x-s-common: 2UQh...
x-rap-param: (GET 没有)
cookie: a1=...; web_session=...
```

注意第三行那个 `image_formats=jpg,webp,avif` —— **逗号是字面量**。第 11 节整篇都在讲这一个字符。

先犯的第一个错误：把 `image_formats` 里的逗号交给 `requests` 去编码。`requests` 用 `quote_plus`，逗号变成 `%2C`，签名照原样算。于是服务端拿收到的 URL 和它自己算出来的签名一比 —— 不一致 —— 返回：

```json
HTTP 406 Not Acceptable
{"code": -1}
```

Body 恒定是这个。`code: -1` 是没有信息量的，它只告诉你"验签没过"，不告诉你是哪一步没过。这一条我卡了很久，后面第 11 节再讲怎么找出来的。

先把三个头拆干净。

| 头 | 长度 | 内容 | 是否随请求变化 |
|---|---|---|---|
| `x-s` | 364（本例） | `XYS_` + 信封 | 每次都变 |
| `x-s-common` | 1292（本例） | `2UQh` 开头 | 每次都变 |
| `x-rap-param` | 变长 | POST body 的压缩加密打包 | 每次都变 |

`x-s` 锁的是**这一条请求**（路径、参数、时间），`x-s-common` 锁的是**这个人**（cookie 指纹、设备信息），`x-rap-param` 锁的是**请求体本身**。三者各管一摊，缺一个都不行。

## 2. 第一刀：XYS_ 剥开是个 JSON

`XYS_` 后面是一段 Base64。但不是标准 Base64 —— 先把这段换回标准字母表，再 `b64decode`，得到一个 JSON：

```python
XYS_ 2UQhPsHC...
       │  decode：先把字符按自定义字母表换回标准字母表
       ▼
{"x0":"4.3.5","x1":"xhs-pc-web","x2":"Windows","x3":"mns0301_...","x4":"object"}
```

实测的字段值（`x3` 省略）：

```text
full x-s length          : 364
x-s prefix               : 'XYS_'
encoded body length      : 360  (pad chars: 1)
json length              : 269
x3 length                : 200
x3 prefix                : 'mns0301_'
x3 encoded part length   : 192
x3 decoded raw length    : 144 bytes
```

也就是说：

- `XYS_` 4 字符
- 编码后的 body 360 字符，末尾 1 个 `=`（269 % 3 = 2）
- 解出来的 JSON 269 字节，其中 `x3` 占 200 字符
- `x3` 去掉 `mns0301_` 前缀，剩 192 字符，解出 **144 字节**

`x0`~`x4` 里，`x0` 是 SDK 版本、`x1` 是 appId、`x2` 是平台、`x4` 是个类型标记，全是明文常量。真正干活的只有 `x3`。

`mns0301_` 这个前缀的形状很像 `<算法代号>_<版本号>`：`mns` 大概是算法代号，`0301` 看着是版本号（**这是从命名惯例推的，没有第二个样本可对照**）。如果这个推测成立，服务端一看到前缀就知道该拿哪套解法去验后面那 144 字节 —— 版本号一变，旧实现直接失效。这也是为什么签名方案必须挂在常量里、随时能改。

顺带一个可以拿来验自己实现的小细节：外层 JSON 永远以 `{` 开头，`{` 的首 6 bit 是 `011110` = 30，查自定义字母表第 30 位是 `2`。所以**`XYS_` 之后的第一个字符一定是 `2`**；`x-s-common` 没有前缀、同样以 `{` 打头，所以它直接以 `2UQ` 开头。（`XYW_` 是例外，它走标准字母表，首字符是 `e` —— 看首字符就能分清当前是哪套信封。）你的实现要是连这个都对不上，前面就白忙了。

## 3. 三套 Base64 字母表，其实只是换表

这个项目里有三套字母表：

```text
标准 : ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/
外层 : ZmserbBoHQtNP+wOcza/LpngG8yJq42KWYj0DSfdikx3VT16IlUAFM97hECvuRX5
x3   : MfgqrsbcyzPQRStuvC7mn501HIJBo2DEFTKdeNOwxWXYZap89+/A4UVLhijkl63G
```

三套都是 64 字符、互不相同。但关键在于：**这不是一种新的编码，只是换了一张字母表**。编码流程就是标准 `b64encode`，然后按表做字符替换：

```python
def encode(self, data_to_encode):
    data_bytes = data_to_encode.encode("utf-8") if isinstance(data_to_encode, str) else bytes(data_to_encode)
    standard_encoded_string = base64.b64encode(data_bytes).decode("utf-8")
    return standard_encoded_string.translate(self._custom_encode_table)   # 就这一行
```

`str.maketrans` 建一张 64→64 的映射，`translate` 扫一遍。解码反着来：先 `translate` 换回标准表，再 `b64decode`。

这层东西的防御价值约等于零 —— 随手把三个表 dump 出来就完了 —— 它唯一的作用是让"直接贴 `base64` 解一段看看"这种最小成本的探查失效，把人挡在门外。

值得注意的是两套表里都有 `+/` 但**没有 `=`**。外层因为 JSON 长度不是 3 的倍数会带一个 `=` 填充符（那个字符不在表里，是原样透传的），`x3` 那层 144 字节正好是 3 的倍数，所以从不带 `=`。

## 4. content_string：一切的源头

144 字节里最重要的两格是两个 MD5，而这两个 MD5 的输入叫 `content_string`。它是整套算法的起点，也最容易出错：

```python
def _build_content_string(self, method, uri, payload=None):
    payload = payload or {}

    if method.upper() == "POST":
        # POST：路径 + 紧凑 JSON，无空格、中文不转义
        return uri + json.dumps(payload, separators=(",", ":"), ensure_ascii=False)
    else:
        if not payload:
            return uri
        params = []
        for key, value in payload.items():
            if isinstance(value, list | tuple):
                value_str = ",".join(str(v) for v in value)
            elif value is not None:
                value_str = str(value)
            else:
                value_str = ""

            encoded_value = urllib.parse.quote(value_str, safe=",")   # ← 逗号
            params.append(f"{key}={encoded_value}")

        return f"{uri}?{'&'.join(params)}"

def _generate_d_value(self, content: str) -> str:
    return hashlib.md5(content.encode("utf-8")).hexdigest()
```

三个要点，一个都不能改：

**一、GET 用 `safe=","`。** 逗号保持字面量，`jpg,webp,avif` 编完还是 `jpg,webp,avif`。整个签名方案里最反直觉的一条：**签名串和最终 URL 的编码规则不是一回事**，签名串按 `quote(safe=",")` 算，而你发出去的 URL 交给 `requests` 会被 `quote_plus` 再编一遍。两者必须手工对齐 —— 这是第 11 节 406 的根源。

**二、参数顺序就是字典的插入顺序。** 没有排序。签名时用的顺序必须和实际发出去的顺序完全一致，`dict` 一旦被重排，签名就废了。

**三、POST 是无分隔符紧凑 JSON，`ensure_ascii=False`。** 中文 `美食` 直接以 UTF-8 原样进入 MD5，不是 `美食`。这里也踩过坑：对照浏览器抓包时，body 里只要多一个空格、或者把中文转成 `\uXXXX`，MD5 就对不上。

实际产出（`user_posted` 那次请求）：

```text
GET  : /api/sns/web/v1/user_posted?num=10&cursor=&user_id=5ff0...&image_formats=jpg,webp,avif
       byte length = 103
       d = 89df9b09a3d78a8627cb4e78685334de

POST : /api/sns/web/v1/user_posted{"keyword":"美食","page":1}
```

GET 请求里那个 `image_formats=jpg,webp,avif` 的逗号，就是它。

## 5. 144 字节结构体，逐格摊开

这是整篇文章的核心。144 字节，14 个字段，全部小端序：

```text
 off  len  字段                                取值/含义
----------------------------------------------------------------------------
   0    4  版本标识                            [121, 104, 96, 41]   (实现里叫 VERSION_BYTES)
   4    4  随机种子 seed (LE u32)               每次生成，参与下面两处 XOR
   8    8  x-t 毫秒时间戳 (LE u64)              请求头里那个 x-t
  16    8  伪 page-load 时间 (LE u64)           x-t 再往前推 10~50 秒
  24    4  sequence (LE u32)                    15~50 随机，模拟会话内序号
  28    4  window props 长度 (LE u32)            1000~1200 随机
  32    4  content_string 字节长 (LE u32)        本例 103
  36    8  MD5(d) 的前 8 字节 ^ seed             路径指纹
  44    1  a1 长度 (u8)                          52
  45   52  a1（不足补 \x00）                      cookie 里的设备标识
  97    1  appId 长度 (u8)                       10
  98   10  appId（不足补 \x00）                   xhs-pc-web
 108   16  环境标志位 (1 + 14)                   1, seed^ENV_TABLE[0], ...
 124   20  a3 前缀 + 自定义哈希 ^ seed             [2, 97, 51, 16] + 16 字节
----------------------------------------------------------------------------
 总长 144（与 PAYLOAD_LENGTH 一致）
```

表格是脚本重建 buffer、然后按 `off` 打印出来的，不是我照源码数格子数出来的 —— 手数一定会错。构造代码本身：

```python
payload = list(self.config.VERSION_BYTES)                 # 4
payload.extend(self._int_to_le_bytes(seed, 4))            # 4

ts_bytes = self._int_to_le_bytes(int(timestamp * 1000), 8)
payload.extend(ts_bytes)                                  # 8

effective_ts_ms = int((timestamp - time_offset) * 1000)   # time_offset ∈ [10, 50]
payload.extend(self._int_to_le_bytes(effective_ts_ms, 8)) # 8
payload.extend(self._int_to_le_bytes(sequence_value, 4))  # 4
payload.extend(self._int_to_le_bytes(window_props_length, 4))  # 4
payload.extend(self._int_to_le_bytes(len(string_param.encode()), 4))  # 4

md5_bytes = bytes.fromhex(hex_parameter)
payload.extend([md5_bytes[i] ^ seed_byte for i in range(8)])   # 8

a1_bytes = a1_value.encode()[:52].ljust(52, b"\x00")
payload.append(len(a1_bytes)); payload.extend(a1_bytes)    # 1 + 52

app_bytes = app_identifier.encode()[:10].ljust(10, b"\x00")
payload.append(len(app_bytes)); payload.extend(app_bytes)  # 1 + 10

part11 = [1, seed_byte ^ self.config.ENV_TABLE[0]]
part11 += [self.config.ENV_TABLE[i] ^ self.config.ENV_CHECKS_DEFAULT[i] for i in range(1, 15)]
payload.extend(part11)                                     # 16

payload.extend(self.config.A3_PREFIX + [b ^ seed_byte for b in self._custom_hash_v2(ts_bytes + md5_path_bytes)])
                                                           # 4 + 16
```

几个值得注意的地方：

**`a1` 占了 52 字节，是全表最大的一格。** 它是 cookie 里一个匿名设备 ID，`ljust(52, b"\x00")` 右补零 —— 说明上游预期 `a1` 恒定是 52 字符。实际它确实恒定 52，所以那个补零分支理论上永远不会触发，是防御性代码。

**长度字段是前缀式的自描述结构。** `1 + 52`、`1 + 10`，先给长度再给内容。好处是解析器不用靠固定偏移硬切，坏处是长度字段一旦被篡改，后面整片错位 —— 而 `a1` 长度写死在偏移 44，改不得。

**第 16 格那个"伪 page-load 时间"很耐人寻味。** 它是 `x-t` 再往前推 10~50 秒，模拟的是"页面在 10 到 50 秒前加载的"。这暗示服务端（或者它的风控）曾经拿这个值去和会话建立时间做比对：如果每次都恰好等于 `x-t`，就说明没有真实页面、每次请求都是当场造的。所以这里必须有偏移。

同理 `sequence`（15~50）和 `window props 长度`（1000~1200）是两格**纯随机会话量** —— 这一点是从代码上能确定的：它们只由随机数生成，**不依赖任何输入**（不进 MD5、不进 content_string）。至于服务端会不会拿它们做别的事，我没法从客户端这一侧证实；能确定的是它们让结构体带上了一层"会话内部状态"的味道。

**变长字段之间没有 padding，靠前缀长度切分。** 整个结构体是紧凑拼接的，一个字节不多。这也意味着 144 这个长度是**算出来**的，不是设定的：4+4+8+8+4+4+4+8 + 1+52 + 1+10 + 16 + 20 = 144。

## 6. 两份 MD5，两处 XOR

144 字节组好之后，过两道异或，再编码。

**第一道：整片 XOR。** 一把 144 字节的固定密钥，逐字节异或：

```python
def xor_transform_array(self, source_integers):
    result_bytes = bytearray(len(source_integers))
    key_bytes = bytes.fromhex(self.config.HEX_KEY)   # 恰好 144 字节
    key_length = len(key_bytes)

    for index in range(len(source_integers)):
        if index < key_length:
            result_bytes[index] = (source_integers[index] ^ key_bytes[index]) & 0xFF
        else:
            result_bytes[index] = source_integers[index] & 0xFF   # 越过密钥的部分原样保留

    return result_bytes
```

密钥长度恰好等于 payload 长度（144），所以 `else` 分支是死代码。这行 `else` 是从更早的实现留下来的：那时密钥短于结构体，尾巴上几个字节不加密。**结构体加长、密钥加长，但那段兼容逻辑没删。** 这种痕迹在逆向里很常见，它本身也是一条时间线索：说明这个格式被扩展过。

**第二道：两格局部异或。** 偏移 36 的 8 字节是 `MD5(d)` 前 8 字节再异或 `seed`；偏移 128 起的 16 字节（前面 124~127 是 `a3` 前缀）是自定义哈希输出再异或 `seed`。为什么在这里还要再异或一次种子？

因为第一道用的是**固定密钥** —— 意味着只要两个请求的原始结构体相同，密文就相同。而 `seed` 是每次随机会话生成的，把它混进这两格，就能保证：**即使路径、时间、a1 全一样，最终 144 字节也不一样**。第 9 节的实验会量化这个效果。

**两份 MD5 的分工：**

```python
content_string = self._build_content_string(method, uri, payload)
d_value = self._generate_d_value(content_string)                    # MD5(路径+参数)
m_value = d_value if method == "GET" else hashlib.md5(uri.encode()).hexdigest()  # MD5(仅路径)

payload_array = self.crypto_processor.build_payload_array(
    d_value,   # → 偏移 36
    m_value,   # → 偏移 124 的 a3 输入
    a1_value, xsec_appid, content_string, timestamp, sign_state=sign_state,
)
```

GET 时两个槽位拿的是同一个 `d`；POST 时第一个槽位是 `MD5(路径 + 紧凑 JSON)`，第二个槽位退回成 `MD5(仅路径)`。

这个设计的意义：**结构体里同时记了"整条请求的指纹"和"这个端点的指纹"。** 服务端拿 POST body 去验证时，第二个 MD5 让它能在不读 body 的情况下先确认"请求打到了我预期的路径上"，再去校验 body。两个 MD5 都对，才说明请求完整。

## 7. a3：一段没名字的哈希

偏移 124 起是一段自定义哈希。前 4 字节是硬编码前缀 `[2, 97, 51, 16]`（ASCII 是 `\x02a3\x10`，`a3` 就是这个字段的名字），后面 16 字节是 `_custom_hash_v2(ts_bytes + md5_path_bytes)` 的输出，再逐字节异或 `seed`。

这个函数不是 MD5、不是 SHA，是自己写的一套带初值、分组的哈希：

```python
def _custom_hash_v2(self, input_bytes):
    s0, s1, s2, s3 = self.config.HASH_IV
    length = len(input_bytes)

    s0 ^= length
    s1 ^= length << 8
    s2 ^= length << 16
    s3 ^= length << 24

    for i in range(length // 8):
        v0, v1 = struct.unpack("<II", bytes(input_bytes[i * 8 : (i + 1) * 8]))
        ...   # 32 位字节序解包，逐块轮转异或
```

输入是 `ts_bytes + md5_path_bytes` = 8 + 16 = 24 字节，正好 3 个 8 字节块。输出固定 16 字节。

特征很明显：先把总长按 4 种偏移异或进 4 个初值（`length`、`length << 8`、`<< 16`、`<< 24`），这是 MurmurHash 系的常见起手式；然后按 8 字节分组、小端解包、做 32 位旋转异或。**它是自研的、刻意不撞现成库** —— 你拿 MD5/SHA 去算，结果永远对不上；反过来，能在逆向里认出"这不是任何标准算法"，本身就说明这段代码被刻意选过。

同一族的还有 `x-s-common` 里的 `CRC32.crc32_js_int`，以及配置里那个用于 gid 的 8 字节 DES 密钥 —— 也是明文硬编码。这些"本地自造 / 非标准"的原语共同构成一层：**让任何基于哈希特征匹配的通用方法全部落空**（拿 MD5、SHA、CRC 去算，结果永远对不上）。

## 8. x-s-common：另一条线

`x-s` 管单条请求，`x-s-common` 管人。它更长（1292 字符），但结构更简单：一个 JSON，同一个自定义字母表（外层表）编一次：

```python
class XsCommonSigner:
    def sign(self, cookie_dict):
        a1_value = cookie_dict["a1"]
        fingerprint = self._fp_generator.generate(cookies=cookie_dict, user_agent=...)
        b1 = self._fp_generator.generate_b1(fingerprint)

        x9 = CRC32.crc32_js_int(b1)

        sign_struct = dict(self.config.SIGNATURE_XSCOMMON_TEMPLATE)
        sign_struct["x5"] = a1_value     # 设备 id
        sign_struct["x8"] = b1           # 指纹摘要
        sign_struct["x9"] = x9           # b1 的 CRC32

        sign_json = json.dumps(sign_struct, separators=(",", ":"), ensure_ascii=False)
        return self._encoder.encode(sign_json)
```

模板里的字段：

```json
{"s0":5,"s1":"","x0":"1","x1":"4.3.5","x2":"Windows","x3":"xhs-pc-web",
 "x4":"4.86.0","x5":"","x6":"","x7":"","x8":"","x9":-596800761,
 "x10":0,"x11":"normal"}
```

它只有三个字段是活的：`x5`（a1）、`x8`（指纹）、`x9`（`x8` 的 CRC32）。`x9` 是 `x8` 的**弱校验** —— CRC32 公开且碰撞容易，所以它显然不是防线；能确定的是它会让"单独改 `x8` 一个字段"变得可检测。至于服务端到底拿 `x9` 做什么，客户端这侧看不出来，我只能说到这儿。

`x8` 是从整个 cookie 集合推出来的指纹，配套一个密钥 `B1_SECRET_KEY`（配置里明文）。所以：**换 cookie 就得重算 `x-s-common`，而且它必须和 `x-s` 用同一套 cookie** —— 这是为什么两个头不能分别来自两个会话。

## 9. 签名为什么不能复用

这套结构里有 3 处随机量：偏移 4 的 seed、偏移 24 的 sequence、偏移 28 的 window props 长度（还有偏移 16 的时间偏移）。所以同一个请求签两次，结果必然不同。

我拿同一个输入签了 12 次，量了和基准的公共前缀：

```text
identical input, identical timestamp, 12 signatures
  all equal          : False
  lengths            : [364]
  common prefix min  : 92
  common prefix max  : 93
  sample prefixes    : [92, 92, 92, 92, 92, 92, 93, 92, 92, 92, 92, 92]
```

三个结论：

1. **长度恒定 364** —— 长度由 JSON 结构决定，随机只影响内容，不影响长度。所以长度本身不是熵的来源。
2. **前 92~93 字符稳定，第 93 位附近开始分叉** —— 稳定的那部分是 `XYS_` + 外层 Base64 里由 `x0`/`x1`/`x2` 和 `x3` 前段决定的位。分叉点之后，密文开始随 seed 变。
3. **12 次全部不相等** —— 完全相同的输入产生完全不同的输出。

推论很实际：

- **签名不可缓存。** 你没法"先算好，需要时再发"。
- **签名不可 diff。** 两个请求的 `x-s` 不同，不能通过比对差异来判断"参数是不是变过了" —— 这条在排错时特别折磨人，我为验证 406 抓过一堆签名，逐字符比对完全没用。
- **只能重新签。** 每次请求必须带着当前时间戳、当前 cookie 重算一遍。

另外顺手量了改参数、改时间戳的分叉位置：

```text
identical input : 92~93
cursor=abc      : 93
ts+60s          : 92
```

**全部落在同一个位置。** 说明改动不会让字符串提前或推后分叉 —— 分叉位置只由 JSON 的字节偏移决定，与输入内容无关。这反过来又是一个可用的自检：你的实现如果发现改了个参数分叉点跑到 60 或 120，那说明前面的编码链已经错了。

## 10. x-rap-param：连 body 也要装袋

GET 请求没有它，POST 请求有。十一个接口里只有两个带 body 的（`search_notes`、`note_feed`）需要 `x-rap-param`。

它的作用是把请求体也打包加密，防止有人"签名合法、body 却在签名之后被换过"。流程大致是：`api path + payload` → 压缩 → 加密 → 包一层协议版本（`XRAP_SDK_VERSION = 10300`）→ Base64。

封装层用一个 `needs_rap: bool` 标在端点配置上：

```python
"search_notes": (SO,  "POST", "/api/sns/web/v2/search/notes", True,  MAIN),
"note_feed":    (EDITH, "POST", "/api/sns/web/v1/feed",       True,  MAIN),
"comment_page": (EDITH, "GET",  "/api/sns/web/v2/comment/page", False, MAIN),
```

实测的规律是：**带 `x-rap-param` 的都是 POST 且走 MAIN 签名**，走 creator 的两个 POST（`search_topic`、`search_user`）反而不带 —— 它们另有一套自己的 body 保护方式。

漏发 `x-rap-param` 的表现不是报错，是**静默返回空数据**，比 406 还难查：请求 200，`success: false`，`payload: []`。你在调参的时候不会怀疑到头字段上。

## 11. 406 的真凶：一个逗号

回到第 1 节。406 只说"验签没过"，不说哪里没过。排查的唯一办法是让自己的实现产出的 URL，和**签名时算的 content_string** 严格逐字节一致。

我把请求发出去前的 URL 和签名用的串并排打出来：

```text
签名算的 : ...image_formats=jpg,webp,avif      ← 逗号是字面量（quote(safe=",")）
实际发出 : ...image_formats=jpg%2Cwebp%2Cavif  ← 逗号被 quote_plus 转义成 %2C
```

差一个字符，签名就废。

根因：`urllib.parse.quote(value, safe=",")` 在签名侧把逗号当字面量，而 `requests` 用 `quote_plus` 在发送侧把逗号转义成 `%2C`。**签名算法和 HTTP 库对同一段文本的编码规则不一致**，而服务端是拿"收到的 URL"去验的，所以必须让发出去的 URL 和签名时用的串完全相同。

修法是不把参数交给 `requests` 自动编码 —— 手工按 `quote(safe=",")` 拼出 query string，直接放进 URL：

```python
def query_url(self, ...) -> str:
    """生成与签名编码器逐字节一致的完整 URL"""
    ...
```

改完之后 406 消失。这条 bug 我记在踩坑表里，因为它是那种**看起来 100% 是签名算法错了、实际是 URL 编码顺序错了**的典型：你越是去怀疑 MD5、怀疑 XOR 密钥、怀疑字母表，越走越远。

顺带一个判断：406 的 body 恒为 `{"code": -1}`。看到它，直接查编码，不要查哈希。

## 12. 两套信封的边界，和一次把会话打废的 461

`XYS_` 不是唯一信封。还有一套 `XYW_`：

```text
XYS_ {"x0":"4.3.5","x1":"xhs-pc-web","x2":"Windows","x3":"mns0301_...","x4":"object"}
XYW_ {"signSvn":"56","signType":"x2","appId":"...","signVersion":"1","payload":"<AES 结果>"}
```

`XYW_` 的 `payload` 是 AES-128-CBC 加密的结果，密钥是配置里硬编码的 16 字节 ASCII 字符串（明文在客户端，任何人打开页面 JS 都能拿到，所以它防的不是有心人，是随手改个参数的脚本）。

还有个立刻能用上的差别：**两套信封的外层编码不同**。`XYS_` 是标准 Base64 之后再按自定义字母表换字符，`XYW_` 直接用标准 `b64encode`。所以 `XYS_` 后面第一个字符永远是 `2`，`XYW_` 后面第一个字符是 `e`。抓到一条 `x-s`，看这一个字符就知道服务端在收哪套东西，不用先解码。

**边界按端点路径划分，不按域名：**

| 路径 | 签名 | 域名/来源头 |
|---|---|---|
| `/api/sns/web/*` | `XYS_`（main） | `www.xiaohongshu.com` |
| `/web_api/*` | `XYW_`（creator） | `creator.xiaohongshu.com` 的 origin/referer |

有个反直觉的点：`/web_api/*` 的请求**实际 host 仍然是 `edith.xiaohongshu.com`**，只是签名换成 `XYW_`、`origin`/`referer` 换成 creator 域名。光看域名会判断错。

**用错的后果是两种完全不同的拒法：**

- 主站路径用错签名 → **406**，body `{"code":-1}`。会话没事，修好了能继续用。
- 创作者路径用错 appId（比如用引擎自带的 `xhs-pc-web` 发给评论接口）→ **461/300011「当前账号存在异常」**。

第二种我撞上了，而且后果比第一种严重得多：**会话被打废，重试救不回来**。判断依据是同一 cookie 换个健康端点（`user/me`）立刻 200，说明 cookie 没过期，是这个特定操作触发了风控。唯一解是换 `web_session`。

这就是为什么我在封装层里按路径自动选签名方案、而不暴露 `sign_format` 给调用方的原因 —— 早期版本留过一个参数让调用方自己指定，它等于把"把会话打废"的按钮交给了使用者。删掉之后，签名方案完全由端点配置决定，外部改不了。

同理，`UNVERIFIED` 这种"未验证也发出去试试"的开关也删了。**一条没人验证过的请求，失败时返回的错误看着和正常错误一模一样**，它污染的是你自己的判断。

## 13. 十一个接口：路径、签名、必填参数

全部通过真实 cookie 实测。表里的 `说明` 是中文，路径是实际发出去的：

| 方法 | 接口 | 路径 | 签名 | 说明 |
|---|---|---|---|---|
| POST | `search_notes` | `so.xiaohongshu.com/api/sns/web/v2/search/notes` | XYS + rap | 关键词搜笔记，返回标题、作者、点赞数，以及后续所有接口都要用的 `xsec_token` |
| GET | `search_filter` | `edith.../api/sns/web/v1/search/filter` | XYS | 搜索结果页顶部筛选项：排序、类型、时间、范围，带服务端分组 id，可回填给 `search_notes` |
| GET | `search_recommend` | `edith.../api/sns/web/v1/search/recommend` | XYS | 输入框联想词。返回 `code: 1000` 但 `success: true`，1000 是正常的「无精确匹配块」码 |
| POST | `search_topic` | `edith.../web_api/sns/v1/search/topic` | XYW(creator) | 搜话题标签，返回话题名、链接、浏览量 |
| POST | `search_user` | `edith.../web_api/sns/v1/search/user_info` | XYW(creator) | 搜用户账号，返回昵称、小红书号、`user_id`、粉丝数，可直接接着调 `user_profile` |
| POST | `note_feed` | `edith.../api/sns/web/v1/feed` | XYS + rap | 单篇笔记详情：正文、标签、点赞/收藏/评论/分享、IP 属地。找不到笔记返回空 `items` 而非报错 |
| GET | `user_me` | `edith.../api/sns/web/v2/user/me` | XYS | 当前登录账号是谁。最省的一次登录态探测，`guest: true` 说明 cookie 已被拒 |
| GET | `user_otherinfo` | `edith.../api/sns/web/v1/user/otherinfo` | XYS | 他人主页资料与统计：笔记数、收藏数、获赞数、关注/粉丝/点赞三项互动 |
| GET | `user_posted` | `edith.../api/sns/web/v1/user_posted` | XYS | 某个用户发布的笔记列表，`cursor` 翻页，回传的 `next_cursor` 原样喂下一页 |
| GET | `comment_page` | `edith.../api/sns/web/v2/comment/page` | XYS | 笔记的一级评论，含每条的 `sub_comment_count` 和首屏子回复 |
| GET | `comment_sub_page` | `edith.../api/sns/web/v2/comment/sub/page` | XYS | 某条评论下的完整子回复，用 `root_comment_id` 定位、`sub_comment_cursor` 翻页 |

### 参数形状是摸出来的，不是猜出来的

这部分没法靠读文档，只能一个个试。几个我试错的例子：

**`search_topic` 的 body 必须嵌套。** 拍平成 `{"page":1,"page_size":20}` → 400。正确形状是：

```json
{"page": {"page_size": 20, "page": 1}, "keyword": "...", "suggest_topic_request": {}}
```

外层还得再挂一个 `suggest_topic_request` 字段，漏了也报错。

**`comment_sub_page` 的参数名是 `root_comment_id`，不是 `top_comment_id`。** 我先按后者发，服务端不报"参数不存在"，而是返回 **`-9109`**，语义是"这个 id 找不到"——**参数名拼错和 id 真的不存在，返回码一样**。这是最坑的一种错：你会一直以为自己 id 传错了，反复换 id。

**子评论翻页必须同时带 `xsec_token` + `image_formats`。** 少任何一个 → **461/300031「当前笔记暂时无法浏览」**。注意这个和 461/300011 是不同子码：30031 是参数不全被拦，30011 是风控。**两个都报 461，但一个是能修的，一个是会打废会话的**，认错子码会让你白折腾很久。

**`user_posted` 是真·无文档接口。** 路径是 `GET`，参数 `num` / `cursor` / `user_id` / `image_formats` / `image_formats` 的值必须是字符串 `"jpg,webp,avif"` 而不是数组（`search_notes` 的同名参数反而是数组）——**同一个参数名在不同端点类型不同**，这是我前后试了十几条才通的原因之一。

**`search_notes` 的 `image_formats` 是数组，`user_posted` 的是字符串。** 同一语义，不同形状，服务端不校验类型时会静默返回空列表。

### 翻页

- 一级评论翻页用 **data 顶层的 `cursor`**；
- 子评论翻页用**父评论对象里的 `sub_comment_cursor`** —— 不是顶层的，也不是 `""`；
- 计数字段（`liked_count`、`sub_comment_count`）是**字符串** `"87"`、`"4"`，不是数字。直接做算术会变成字符串拼接。

## 14. 错误码对照表

实测撞到过的，按"能不能自己修"分三类：

| 状态/码 | 表现 | 能不能自己修 | 处置 |
|---|---|---|---|
| `406` `{"code":-1}` | 验签失败 | ✅ 能 | 查 URL 编码顺序、查 content_string，别查哈希 |
| `400` | body 形状错 | ✅ 能 | 对照浏览器抓包改结构（多半是漏了嵌套层） |
| `-9109` | 说找不到 | ⚠️ 一半 | 先确认参数名拼写，再怀疑 id —— 两者的返回码一样 |
| `461/300031` | 「当前笔记暂时无法浏览」 | ✅ 能 | 参数不全，补 `xsec_token` + `image_formats` |
| `461/300011` | 「当前账号存在异常」 | ❌ 不能 | **会话已废**，换 `web_session`，重试无效 |
| `461/471` | 要人解验证码 | ❌ 不能 | 停手，别继续刷 |
| `success:false` + 200 | 无数据 | ⚠️ 一半 | 先查 `x-rap-param` 漏没漏，再查参数 |
| `code:1000` + `success:true` | — | — | **正常**，不是错误 |

最后三行是最值钱的：**它们都不会以"错误"的形态出现**。200 + 空 payload、`code:1000` 带 `success: true`，如果你的调用层只判 `status_code`，这三种你一个都发现不了。

## 15. 收尾：能复现的才算数

这条我在这个项目里反复强调，也确实踩过坑：曾经有一个接口被列进"已验证"，实际上从来没真正跑通，一跑才发现在骗自己。**列表里写了，不等于真的能用。**

所以现在的规矩是：

- 配置表里只放实测通过的端点，查一个不存在的名字直接抛 `KeyError` 并列出已知键，而不是发一个没人验证过的请求；
- 测试分两层：**离线测试**（51 个用例）覆盖结构构造、归一化、406 回归 —— 不联网；**端到端验证**（14 项）拿真实 cookie 跑一遍；
- 任何参数名、字段名、返回码，**没实测过的不写进文档**。

回头看，144 字节那张表本身不难，难的是确认它是对的。所有数字我都用脚本重建 buffer、按偏移打印、再和实际签名的解码结果比对 —— **手推出来的偏移表看着合理，一验就错**（我第一版手推的 JSON 长度就是 267，实测是 269，差在引号上）。

同样的道理，那 11 个接口、每条的必填参数、每个错误码，也是撞出来的而不是查出来的。小红书这套接口没有对外文档，`-9109` 这种语义模糊的返回码更是把"参数名写错"伪装成"id 不存在"。在没有文档的地方，**唯一可信的证据是服务端的回应**，而判断它真不真，只能靠把每个假设都跑一遍。

这套东西会变，`mns0301` 里那个 `0301`（如果是版本号的话）哪天变一变，这篇文章的大半代码就失效了。但构造思路大概不会变：**明文结构体 + 随机种子 + 固定密钥混淆 + 自定义字母表编码**，外加**按路径划分的两套信封**。看懂一次，下次换版本大概知道该往哪看。
