**边界。** 不修改任何游戏进程，不运行样本的修改功能，样本仅在受控提权环境中短时运行 12 秒用于行为观测，结束后立即终止；不提供反作弊规避实现、补丁数据或任何可直接用于第三方游戏环境的材料，文中地址与脚本片段仅用于说明分析方法；样本仅在本地文件系统内分析，指纹见第 1 节。

本文的写法是按攻击面推进：先看文件里有什么，再看文件里搜不到什么以及为什么搜不到，然后逐层打开加密部分与运行期行为，最后把结论重写成可编译、可自测的代码。静态分析用 `pefile` 与 `capstone` 手工反汇编，托管部分用 `ildasm`，全部地址在 ImageBase `0x140000000` 下以 RVA 标注；标"推断"者为证据链支撑但未经直接验证的判断。

## 1. 样本与三段式结构

文件指纹如下，机器无关，可直接用于比对：

| 项 | 值 |
| --- | --- |
| 大小 | 1,689,088 字节 |
| SHA256 | `F5B7FD6CF17F5D0A8F5FAA7C59AD022CB206F8F738E7B87AC3AD2AF16C4B0387` |
| 格式 | 64 位 PE，7 节（.text/.rdata/.data/.pdata/.fptable/.rsrc/.reloc） |
| ImageBase / 入口 | `0x140000000` / RVA `0x9F4E0` |
| 子系统 / DLL 特征 | GUI(2) / `0x8160`（ASLR、DEP、动态基址、终端服务器感知） |
| 签名 | 无；清单 653 字节，`requireAdministrator` |

两个商标同时出现，是二次打包的典型指纹：FLiNG 出的修改器被国内站点转手重编译或重打包，但静态证据不足以判定方向，结论维持推断。清单要求管理员权限，直接后果是样本无法以普通权限启动（运行时报 `WinError 740`），这一点与第 4 节的提权链构成两层权限设计。

资源树枚举后，结构一目了然：

| 资源 | 大小 | 性质 |
| --- | --- | --- |
| `/UI/101` | 198,656 B，熵约 7.8 | 加密的托管程序集，第 3 节打开 |
| `/REMOTE/250` | 142,848 B | 变速 DLL，x64 PE，时间戳 2024-03-31 |
| `/REMOTE/246` | 4 B（`0xFFFFFFFF`） | 远程开关或版本标志，用途未追 |

**三段式结构是本文的主线。** 原生壳负责进程枚举、内存读写与热键，UI 是被加密封装的 WPF 程序集，变速能力放在第二块 PE 里注入游戏，23 项功能则以明文脚本形式挂在壳内。三部分分处三种保护强度之下，本身就是一份防御强度分布图：业务逻辑最不设防（明文），UI 中等（可逆加密），真正的进程操作能力藏在托管层与加密串的双重遮蔽下。

## 2. 静态陷阱：导入表不等于能力清单

把"敏感 API 清单"拿去导入表里点名，结果全部落空：

| 检索项 | ASCII | UTF-16 |
| --- | --- | --- |
| OpenProcess / ReadProcessMemory / WriteProcessMemory | -1 | -1 |
| CreateRemoteThread / VirtualAllocEx | -1 | -1 |
| GetAsyncKeyState / SetWindowsHookEx | -1 | -1 |
| `http://`、`https://`、`winhttp`、`ws2_32` | -1 | -1 |
| CreateNamedPipeW | -1 | -1 |

一个 23 键修改器，导入表里没有进程读写、没有键盘钩子、没有任何网络字符串，而 23 条要改游戏内存的脚本明文躺在文件里。矛盾的原因有三条通道。

其一，**运行时解析**。全文件 `GetProcAddress` 的间接引用共 26 处，排列成两簇（12 处与 10 处，另有 3 处零散、1 处在 main），同簇内相邻调用点间距稳定在 `0x1A4` 至 `0x1C6` 字节，是同一函数体被宏或模板复制的痕迹。解析结果被写入运行时构造的函数指针表（`mov [rsi+8], rax`），配套的 `LoadLibraryA` 有 5 个调用点。静态上连 API 名称本身都不存在，说明名称或拼接构造，或位于托管层。

其二，**托管层解析**。`mscoree.dll` 只导入一个 `CLRCreateInstance`，这是托管宿主的入场券；.NET 自身的 P/Invoke 走 CLR 内部解析，宿主 EXE 的导入表不体现。main 开头即 `SetProcessDPIAware()` 与 `CoInitializeEx(NULL, COINIT_APARTMENTTHREADED)`，配合该导入指向 WPF 实现的 UI（动态侧的 `PresentationFramework.ni.dll` 加载为实证）。

其三，**字节码层面**。高熵资源未解密前，其中的内容不可检索。

检索本身也有一个值得记录的负结果。在 `.rdata` 中检索 `NamedPipe`，ASCII 命中一处，形似管道名被找到，实际是从 `WaitNamedPipeW` 中间断出的片段：该区域是标准 PE 导入名表（`[Hint: u16][名称\0]`，偶数对齐），`\xf4\x03` 是 LoadLibraryA 的 hint，`\xa9\x04` 是 ReadFile 的 hint。真正的 `FLiNGTrainerNamedPipe_` 在双编码下全文零命中，结论是这个名字在运行时拼装，第 5 节会看到拼接代码。

**方法上的结论有两条。** 静态检索的负结果只能证明"不在导入表与明文串中"，不能证明"不具备该能力"；任何"未检出"结论都必须标注置信级别，否则会把工具的局限误记为样本的性质。

## 3. 已知明文攻击打开加密资源

`/UI/101` 熵约 7.8，单字节 XOR 未能还原。突破口不是猜算法，而是猜明文：PE 头的字段几乎全是已知的，`MZ` 魔数、`e_lfanew` 指向的 `PE\0\0`、可选头里的 `0x20B`（PE32+）都是固定模式。用这些字段与密文对拍，重复 XOR 的周期立刻确定：

```python
# 已知明文对拍，周期 32 字节，密钥取自密文自身
cipher = blob[:64]
for period in range(1, 65):
    key = bytes(c ^ t for c, t in zip(cipher[:period], template))  # MZ/e_lfanew/PE\0\0/0x20B
    plain = xor_repeat(blob, key)
    if plain[:2] == b'MZ' and struct_ok(plain):      # e_lfanew 与 PE 签名自洽
        break                                         # → period = 32
```

解开后是完整的 .NET 程序集 `FLiNGTrainerGUI_WPF.exe`，1.47 MB IL 文本、37 个类。资源树中没有第三块 PE，第 1 节的三段式结构由此闭合。

托管层的职责边界随之明确：37 个类中 `MainWindow`、`Utils`、`AppSettings`、`TrainerSettings`、`UILanguage`、`UIText` 各司其职，9 个 P/Invoke 全部是 `GetAsyncKeyState`、窗口句柄这类轻量调用，**托管层不碰内存也不碰进程**，重活全在原生壳与变速 DLL。资源树里"没有第三块 PE"这一条同时排除了更隐蔽的投放组件。

## 4. 字符串保护：从约减例程反推 LCG

`OpenProcess`、`WriteProcessMemory` 这些名称从未以明文形式存在，它们以密文形态躺在 `.text` 的指令立即数里，运行时现解现用；解码函数有二十余个同族变体（`0x33d20`、`0x338b0`、`0x39d70` 等），按输出类型与长度模板实例化。突破口选在解码器本体的约减例程，即编译器为取模 `2^31-1` 展开的乘移序列：

```asm
mul  3                    ; 3a
; 取商高 32 位 → edx
shr  30                   ; 商 q
imul 0x7FFFFFFF
sub                        ; 余数
```

翻译为公式与状态机，三个常量即钉死整个保护方案：

```text
reduce(a) = a − ((a>>1 + ((3a)>>32)) >> 30) × (2^31−1)   ≡   a mod (2^31−1)

state₀     = 0xD6E42661
plain[i]   = (stateᵢ & 0xFF) XOR cipher[i]
stateᵢ₊₁   = (stateᵢ × 0xBC8F) mod (2^31−1)
```

这是一条 LCG（线性同余生成器）流密码，验证方式是双重的：先用一万个随机数确认 `reduce(a) == a % 0x7FFFFFFF`，再用二进制内的真实密文对拍，两者全过。

**打法上做了一次转向：不追调用点，改扫常量。** `mov dword ptr [栈槽], 0xD6E42661` 这一立即数在 `.text` 中出现的次数，就是加密点数量，45 处，一处不漏。每个位点形态相同：密钥后 4 字节起是密文，由 `movdqa`（16 字节 RIP 相对块）与若干立即数拼装。

```asm
mov   dword ptr [rsp + 0x20], 0xd6e42661   ; 密钥
movdqa xmm0, xmmword ptr [rip + 0x9f5b9]   ; 密文 16B
movdqu xmmword ptr [rsp + 0x24], xmm0      ; 数据基址 = 密钥槽 + 4
mov   dword ptr [rsp + 0x34], 0xb2ce8f73   ; 续 4B
mov   dword ptr [rsp + 0x38], 0x36f1ea2d   ; 续 4B
mov   byte  ptr [rsp + 0x3c], 0xde         ; 尾 1B
mov   r8d, 0xd6e42661                      ; 解码器第 3 参 = 密钥
```

两处坑值得记：RIP 相对的 `movdqa` 载荷有时出现在**密钥存储之前**，向前回溯范围不足会漏掉前 16 字节；`xmm0/xmm1` 两段存储必须按寄存器配对回溯，按"最近一条"配对会取错源。修完后 45 个位点全部解出，归并去重得 39 个唯一串（4 个 DLL 名各重复 2 至 4 次，均为"加载加解析"的成对代码），并发现一处分片存储：`https://flingtrainer.com/tag/` 被拆成 16+16 两段，第二片从头解是乱码，按状态续算 16 步再解才正确，分片结构本身即证明算法为流密码。

解出的隐藏能力清单，是这份样本最完整的一面：

| 类别 | 解出的串 |
| --- | --- |
| 要加载的 DLL | `Kernel32.dll`×4、`Advapi32.dll`×2、`User32.dll`×2、`Shell32.dll`×2 |
| 进程枚举 | `OpenProcess`、`CreateToolhelp32Snapshot`、`Process32FirstW/NextW`、`Module32FirstW/NextW`、`K32GetProcessMemoryInfo`、`CreateProcessW`、`TerminateProcess` |
| 提权 | `OpenProcessToken`、`AdjustTokenPrivileges`、`LookupPrivilegeValueW` |
| 内存与注入 | `ReadProcessMemory`、`WriteProcessMemory`、`CreateRemoteThread`、`VirtualAllocEx`、`VirtualFreeEx`、`VirtualQueryEx`、`VirtualProtectEx` |
| UI 与杂项 | `FindWindowW`、`GetAsyncKeyState`、`ShellExecuteW` |
| 协议常量 | `FLiNGTrainerNamedPipe_`、`TRAINER_INITIALIZE`、`CHECK_UPDATE`、`CUSTOM_INIT_MESSAGE`、`SET_GAMEPASS_EXE_PATH`、`ENABLE_ANTICHEAT_BYPASS`、`{CMD}_SetLanguage`、`{CMD}_InstallAnticheatBypass`、`CHADURL`（明文） |
| URL | `flingtrainer.com/cn/2.html`、`flingtrainer.com/tag/`、`bbs.3dmgame.com/thread-`、`-1-1.html` |

这张表有三个直接读数。**提权链是完整的**：`OpenProcessToken` → `LookupPrivilegeValueW(SeDebugPrivilege)` → `AdjustTokenPrivileges`，即在清单要求之外再加一层运行时提权。**注入四件套齐全**：读、写、分配、远程线程。**表中没有 `CreateNamedPipeW`**，原生侧只有客户端资格，服务端必在托管层，第 5 节的 IL 证据与此互为闭环。

## 5. 进程内双通道与帧协议

管道客户端在 `0x3DC40`，核心逻辑自 `Sleep` 调用开始，语义还原如下：

```c
// esi 为毫秒级预算，由调用方装填
bool pipe_connect(ctx* self, const wchar_t* name, int budget_ms) {
    do {
        Sleep(10);
        if (WaitNamedPipeW(name, 10)) break;                  // 管道已建立
        if (GetLastError() != ERROR_FILE_NOT_FOUND) break;    // 其他错误，放弃等待
        budget_ms -= 10;
    } while (budget_ms > 0);

    HANDLE h = CreateFileW(name, GENERIC_READ | GENERIC_WRITE, 0, NULL,
                           OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, NULL);
    self->pipe = h;                                           // 存入 [this+8]
    return h != INVALID_HANDLE_VALUE;
}
```

每轮先睡 10 毫秒再探测，`WaitNamedPipeW` 自身超时也是 10 毫秒，属双重保险的忙等规避写法；错误处理只对 `ERROR_FILE_NOT_FOUND`（管道尚未建立）继续等待，管道被独占时反而直接 `CreateFile` 尝试。名称为前缀 `FLiNGTrainerNamedPipe_` 加自身进程号三段拼装，与第 2 节"全文搜不到全名"的结论吻合。

服务端在托管层，IL 直接给出实证：

```il
.field private class [System.Core]System.IO.Pipes.NamedPipeServerStream m_named_pipe
.method InitializeNamePipe(string name)
    ldc.i4.3          // PipeDirection.InOut
    ldc.i4.1          // maxNumberOfServerInstances = 1
    ldc.i4.0          // PipeTransmissionMode.Byte
    ldc.i4  0x80000000 // PipeOptions.Asynchronous
    newobj NamedPipeServerStream::.ctor(...)
    callvirt WaitForConnection()
```

两处调用点都是 `ldstr "FLiNGTrainerNamedPipe_"` 加 `Process.GetCurrentProcess().Id` 拼接后传入，全程无 P/Invoke。

**架构结论：一个 EXE 内运行两套运行时，两条通道分工明确。** 命名管道承载请求与应答，内存映射文件（MMF）承载状态共享；共享内存不具备应答语义，命令回执必须走管道，属设计选择而非冗余。触发时机为主线程在找到游戏进程后加载辅助数据、构造会话对象并拉起管道，管道生命周期与游戏进程的存在绑定。

帧格式在托管侧的读写函数中全裸呈现，无需推断：

| 语义 | 线上格式 |
| --- | --- |
| 字符串 | `[i32 LE 长度][字节载荷]`，读侧先 `ReadInt32` 再 `Read` 满载荷，解码为 `Encoding.Default`（GBK）或 `Encoding.Unicode`（UTF-16LE） |
| 应答值 | 裸 `[i32 LE]`，`BitConverter::GetBytes` 后直接 `Write`，无长度头 |

原生侧与之严丝合缝：读取应答即 `ReadFile(h, buf, 4, ...)`，恰好一个 int32。命令共 12 条，`CHADURL` 握手并下行 URL（存进 `UrlAdCH`）、`RESETCHADURL` 复位、`WMURL` 打开页面、`SETTINGS` 与 `SAVE_SETTINGS` 设置同步与保存、`SET_GAMEPASS_EXE_PATH` 下发游戏启动路径、`ENABLE_ANTICHEAT_BYPASS` 反作弊绕过开关、`TRAINER_INITIALIZE` 初始化、`CUSTOM_INIT_MESSAGE` 自定义启动消息（经 `Dispatcher.Invoke` 回 UI 线程）、`CHECK_UPDATE` 更新检查、两条 `{CMD}_` 模板族。分发器逐条 `String.op_Equality` 比对，命中回 `WriteValue(1)`，**未命中回 `WriteValue(0)`**，即协议自带 NACK，错误路径完整。

握手时序可完整还原：原生侧发 `[len]"CHADURL"`，托管侧 `ReadString()` 命中并回裸 i32 1，原生侧再发 UTF-16 的 URL。附带一个例外：`0x40f40` 处的握手函数把 `"CHADURL"` 以两个 dword 明文直接压栈后调 `strlen`，在 45 个加密位点中属唯一明文，是疏漏还是刻意设置无从考证。

**双端对账是这份样本最省力的武器**：原生侧的密文与托管侧的明文互为字典，一条链的输出是另一条链的输入，对不上的位置即未解完的位置。

## 6. 23 项功能：脚本机制与三种典型补丁

修改器的功能主体不是两万多行原生代码，而是 23 条 Cheat Engine 风格自动汇编脚本，明文存放。解析器为自带，全文件唯一一处 `aobscanmodule` 关键字引用即分发点（`lea rdx, [rip + 0x62105]` → `call 0x84e50`），无需外部 Cheat Engine。脚本套路三步：`aobscanmodule` 按字节模式在目标模块定位 → `alloc` 开一块可执行区，把原指令搬入并补钩子逻辑，原址改写为跳转 → `[DISABLE]` 段把原字节逐字节写回。

三种典型补丁代表了三种改法。

**改数据。** 锁血脚本扫描串 `48 85 C9 48 0F 44 D7 C5 FA 10 32 A8 01 0F 85` 对应"判空后取浮点血量"的形状，钩子仅 7 字节（`jmp newmem` 加两字节 nop），洞内逻辑是判空、加寄存器、改 `[rdx+04]` 为记录的上限值，再按 `godmode` 与 `health` 两个开关决定是否 `fadd` 一万点浮点后 `fstp` 写回，开关由 `registersymbol` 注册为全局符号供 UI 写入。

**改数据而不改控制流。** 技能冷却脚本扫描 `48 0F 44 C8 48 39 4F 68`（`cmove` 加 `cmp [rdi+68], rcx` 加 `jbe`），洞内只做一件事：比较前把 `[rdi+68]` 清零，随后把原比较重做一遍以保留标志位语义，后续依赖 ZF 的分支不受影响。改写量是一行，但保留了完整的数据流语义，比硬改跳转更干净。

**等长换芯。** 潜行脚本不开洞：`0F 85` 是 6 字节的 `je rel32`，`E9` 是 5 字节的 `jmp rel32`，把前两字节换成 `90 E9`（一字节 nop 加五字节 jmp），长度仍为 6，位移 4 字节原封不动，落点与原 `je` 完全相同，语义从条件跳变为无条件跳。`[DISABLE]` 只需写回 2 字节即可完整复原，后续指令一个字节都不用移动。这是补丁技术中最值得掌握的一类：指令改写不必等长，等长即可免去重定位。

23 项功能按实现手法归为五类，功能名与实现方式的对应关系由 ID 命名（`_f` 后缀即 float）与帮助串措辞共同确定，未逐条展开的标推断：

| 类别 | 数量 | 代表项 |
| --- | --- | --- |
| 钩子补丁型（AOB 定位后改逻辑，等事件不轮询） | 9 | `godmode`、`skills_instant_cooldown`、`stealth_mode`、`infinite_oxygen` |
| 数值与倍率型（读出后乘或写回） | 7 | `dmgmul_f`、`defmul_f`、`expmul_f`、`selected_item`、`mastery_points` |

三方对账成立：文件名中的"23"、文件内 `[ENABLE]` 块数量（23）、动态观测到的窗口标题"二十三项修改器"一致，分组为数字键 13 条加 Ctrl 组 10 条，帮助串中还有 `<input_set default="99999">` 一类标签，供 UI 渲染数值输入框。变速能力的实现载体是资源里的 `TrSpeedHack_x64.dll`（`num_names = 0` 的序号导出，导入含 `SuspendThread`、`ResumeThread`、`GetThreadContext`、`SetThreadContext`、`CreateToolhelp32Snapshot`、直连 `WINMM!timeGetTime` 与 `QueryPerformanceCounter`），即"枚举线程 → 挂起 → 改计时 → 恢复"的内联钩子施工法。

## 7. 动态验证与连接归因

受控提权运行 12 秒，逐秒采样，观测结果：

| 项 | 观测值 |
| --- | --- |
| 窗口 | "刺客信条：影 v1.0-v1.1.8 二十三项修改器" |
| 加载模块 | `clr.dll`、`clrjit`、`mscorlib.ni.dll`、`PresentationFramework.ni.dll`、`mscoree`，GAC 内另有 UIAutomation 与 zh-Hans 资源 |
| 规模 | 线程 28、句柄 738、DLL 141、RSS 114.5 MB、CPU 14.3% |
| 管道 | `FLiNGTrainerNamedPipe_<pid>` 存在，进程退出即消失 |
| 子进程 / 新文件 | 无 / 无 |
| 网络栈 | `winhttp`、`ws2_32`、`schannel`、`secur32`，均不在静态导入表内 |
| 连接 | 2 条 ESTABLISHED，IPv6 `:443` → `2606:4700:20::ac43:491a`，全程保持 |
| DNS 增量 | 仅 `gfe.nvidia.com`，属无关噪声 |

三点结论。其一，CLR 与 PresentationFramework 的加载把第 2 节"UI 由 WPF 实现"的静态推断转为实证。其二，管道名带进程号后缀，解释了为何全文检索不到该字符串。其三，无子进程、无新增文件，可排除下载器与投放器行为。

**矛盾在网络一侧：** 静态侧 9 个导入 DLL 中无任何网络库、144 个导入函数中无网络相关项、双编码检索下 `http://`、`https://`、`winhttp`、`ws2_32` 全部零命中；动态侧四个网络 DLL 进入地址空间，两条 TLS 长连接挂满全程。两者都不算说谎，静态导入表只登记编译期确定要链接的 API，托管层一次 `WebClient` 调用即由 CLR 内部拉起整套 HTTP 栈，而托管程序集封在加密资源内，域名自然无法静态检索。

**归因不需要中间人。** 托管层 IL 中的 URL 为明文，取 `flingtrainer.com` 的 AAAA 记录逐一比对：

```text
flingtrainer.com  A    : 104.26.14.72, 172.67.73.26, 104.26.15.72
               AAAA : 2606:4700:20::681a:f48,
                      2606:4700:20::ac43:491a,   ← 与观测端点逐字节一致
                      2606:4700:20::681a:e48
```

观测端点 `2606:4700:20::ac43:491a` 命中该域名的 AAAA 记录，且其低 32 位对应的 A 记录为 `172.67.73.26`，v4 与 v6 互相印证，两条连接由此归因到更新检查与账号登录两个接口。方法可复用于任何"只拿到 IP 与端口"的场景：先看地址段归属（本例为 Cloudflare 段 `2606:4700::/32`），再用候选域名的解析记录做逐字节比对，比对成功即完成归因，不必触碰 TLS。

实践含义是两条证据各有分工：静态负责给出能力清单的骨架与否定证据，动态负责给出实际行为，仅凭"静态零网络"放行会漏判，仅凭"存在长连接"定罪会误伤。

## 8. 重建：把看懂变成可测

逆向结论的可信度取决于能否独立重写，因此最后一步是把前述理解落成工程 `fling_trainer_rebuild/`，逐层对照：

| 层 | 原样本 | 重建实现 | 关系 |
| --- | --- | --- | --- |
| 字符串保护 | LCG 流密码，20 余个解码器变体，45 位点 | `lcg_codec.h` 单一实现，并**补写 `encode()`** | 算法 1:1（37 条向量对拍） |
| API 解析 | 39 个名称加密存放，运行时解析 | `attach.h` 明文调用等价 API | 能力等价，去混淆 |
| 管道客户端 | `0x3DAC0`：10 毫秒粒度轮询，10 秒预算 | `pipe_client.h` 忠实版 + 优化版 | 指令级复刻，可优化 |
| 管道服务端 | WPF `m_named_pipe` | `pipe_server.cs` 同名同参复刻 | 方法级复刻，`csc` 可编译 |
| 帧协议 | `[len][payload]` + 裸 i32 应答 | `pipe_proto.h`，12 条命令全集 | 帧格式 1:1 |
| AOB 定位 | CE 脚本 `aobscanmodule` 内联 | `aob_scan.h` 通配扫描 + 1 MB 分块读 | 能力等价，含分块优化 |
| 功能开关 | 23 条脚本 + GUI 事件散落 | `features.h` 单一数据表 23 行 | 结构性修改 |
| 热键 | `GetAsyncKeyState` 电平轮询 | `hotkey.h` 上升沿触发 | 语义不变，防按住连发 |

核心算法重写如下，`encode()` 是原实现所没有的，补上后改密钥与新增字符串都在源码层完成：

```c
static inline uint32_t reduce31(uint64_t a) {          // a mod (2^31 - 1)
    return (uint32_t)(a - (((a >> 1) + ((3 * a) >> 32)) >> 30) * 0x7FFFFFFFu);
}
void decode(const uint8_t* cipher, char* out, size_t n, uint32_t seed) {
    uint32_t s = seed;
    for (size_t i = 0; i < n && cipher[i]; ++i) { out[i] = (char)((s & 0xFF) ^ cipher[i]); s = reduce31((uint64_t)s * 0xBC8Fu); }
    out[i] = '\0';
}
void encode(const char* plain, uint8_t* out, uint32_t seed) { /* 同一状态机反向 */ }
```

优化项五条，均已落代码。管道连接由 10 毫秒粒度轮询（10 秒预算即最多 1000 次往返）改为 250 毫秒切片，往返不超过 40 次，连接语义不变；AOB 扫描改为 1 MB 分块读加 `(patlen-1)` 重叠窗口、首字节预筛，并用 `VirtualQuery` 跳过 GUARD 与 NOACCESS 页，块间不漏报且系统调用次数降一个量级；写路径补上属性还原（`VirtualProtectEx` 改属性 → 写入 → 恢复原属性 → `FlushInstructionCache`），原样本的写路径不带这层；功能表数据化后加功能只需加一行数据，引擎不动；热键改上升沿触发，避免按住连发。

构建与自测用本机现成工具链：VS2017（MSVC 14.16，WinSDK 10.0.17763）加 .NET Framework 的 `csc.exe`，`vcvars64.bat` → `cl /std:c++14 /utf-8 /O2` → `csc /target:library` → 自测，`build.bat` 一条线串起。过程中三个真实错误值得记录：命名空间 `inline` 变量需 `/std:c++17`；`SE_DEBUG_NAME` 在非 UNICODE 下是窄串，`LookupPrivilegeValueW` 需换 `…A`；`OpenProcessToken` 一族在 `advapi32.lib`，默认不链。还有一处测试缺陷：自测断言按整块密文比对，而原实现语义只保证到 NUL，密文尾部存在对齐残渣，断言改为"前缀到 NUL"才反映真实契约。

自测共 18 项，17 项通过，1 项按预期跳过（当前会话无管理员令牌，提权路径无法验证，输出标 `[SKIP]` 而非 `[PASS]`，不伪造绿灯）。三项具有独立价值的断言：37 条密文向量逐条对拍二进制原文；管道环回，即新建服务端线程、原生客户端按 `FLiNGTrainerNamedPipe_<pid>` 连接、发送 `CHADURL` 帧、收到裸 i32 应答 1、回送 UTF-16 载荷；远程路径实测，用 `ReadProcessMemory` 在自身镜像内分块扫描出预埋标记。产物 `out\trainer.exe` 提供 `--selftest`、`--attach <exe>`（只读探测）与 `--patch-demo`（仅对自身缓冲区演示写路径）三个子命令。

**未验证项如实列出。** 23 条补丁的实机匹配需要游戏本体，本次未做；管道自测为本进程环回，不接触原样本进程；提权路径因会话权限限制未验证。重建工程的定位是可执行验证而非复刻品：它证明的是算法、协议与结构能被独立重写并测绿，反作弊绕过链路未追，重建工程也刻意不含该部分实现。

## 9. 方法论、工具与未验证项

五条可迁移的做法，按收益排序：

1. **已知明文先行。** 不要先猜加密算法。PE 头、可执行文件格式、时间戳、结构体布局都是白送的明文，对拍即可定周期，对加密数据尤其有效。
2. **搜常量而非追调用点。** 加解密密钥以立即数形式出现在代码中，其字节模式比调用点更稀有、更稳定，一次扫描即可穷举全部加密位点。本例中 45 个位点由一个 4 字节常量的出现次数确定。
3. **双端对账。** 同一份逻辑的两种实现（本例为原生密文与托管明文）互为字典，输出输入成对，比单侧分析快一个量级。
4. **负结果同样记录。** 检索落空的原因往往本身是结论，本例"搜不到管道名"直接指向运行时拼装。
5. **重建即验证。** 把理解写成能编译、能运行、能自测的代码，是"推断"升级为"结论"的分界线；测试写得比实现更苛刻时，通常是测试错了。

环境与工具：`py -m pip install pefile capstone psutil` 做探针，`ildasm /text /bytes /utf8` 处理托管程序集，`vcvars64.bat` 负责构建。三个环境坑：Windows 控制台为 GBK 编码，Python 或 bat 中直接输出中文会抛 `UnicodeEncodeError` 或把注释行当命令执行，需强制 UTF-8 或把批处理文件限定为纯 ASCII 加 CRLF；`python` 命令可能是损坏的存根，需改用 `py` 启动器；查 IAT 时若忘记加 ImageBase，全部地址会返回 `NOT FOUND`。

本篇的适用边界同样明确：样本未签名、来源为第三方下载页、含加密黑盒与运行时联网，五路证据指向作者为风灵月影（FLiNG），再打包方无签名证据故维持推断；恶意证据未出现（无落盘、无子进程、无注入动作），但在能独立验证之前，误报与真实的区别并不存在。
